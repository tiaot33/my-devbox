# 用途：约定

## 判定

- 读者读完要遵守、执行或签认；之后有争议时，拿它当准绳。
- 典型文档：团队规范、编码约定、协作流程、值班制度、SLA、内部管理办法、评审标准。
- 容易混淆：
  - 用户协议、隐私政策 → `legal-terms.md`。
  - 需求规格、PRD → `requirements.md`。
  - CONTRIBUTING、行为准则 → `lifecycle-other.md`。

## 结构

1. **目的与范围**：为什么定这份约定，适用于谁、哪些场景，不适用于哪些。
2. **术语**（可选：有本约定专用的词时）。
3. **条款**：编号的条目，每条一个要求。
4. **例外与申请**：什么情况可以不遵守、向谁申请、谁批准。
5. **生效与修订**：生效日期、负责人、怎样提修改。

## 写作规则

- 每条写明谁、在什么条件下、必须做或不得做什么："合入主干的变更必须有一名非作者批准"。
- 只用 `base.md` 的受控情态词；"尽量""原则上"改成具体条件，或删掉。
- 每条都能判定是否遵守；判定不了的，补上可检查的标准或改成建议并写明理由。
- 条款编号一经发布不重排；删除的条款写"已删除"并保留编号。
- 理由可以跟在条款后，用一句话；理由不改变条款的意思。

## 要读的内容块

- 无必读块。条款里有操作过程时读 `blocks/steps.md`。

## 审查清单

- [ ] 写明了适用范围和不适用的情况。
- [ ] 每条写明了主体、条件和要求。
- [ ] 每条都能判定是否遵守，没有"尽量""原则上"。
- [ ] 写了例外怎样申请、由谁批准。
- [ ] 写了生效日期和负责人。
