# 用途：决定

## 判定

- 读者读完要做决定、批准、调资源，或判断事情是否在正轨。
- 典型文档：周报、月报、项目进展、方案对比、技术选型、提案、复盘的结论部分、调研结论。
- 容易混淆：
  - Agent 给用户的结果汇报 → `agent-report.md`。
  - 科技报告 → `tech-report.md`。
  - 复盘：用户只要留档经过和原因 → `genre/record.md`；要定改进措施，或两者都要 → 本用途，时间线放进"细节"。

## 结构

1. **结论和请求**：第一段写结论，以及要读者做什么、什么时候之前做。没有请求时写"无需决定"。
2. **依据**：支撑结论的事实和数据，最重要的在前。
3. **选项**（可选：要读者在几种做法里选时）：每个选项写代价、收益、风险，作者推荐哪个及理由。
4. **风险与未决事项**：会影响决定的未知数，各写由谁、何时弄清。
5. **细节**（可选）：完整数据、过程，放在最后或附录。

## 写作规则

- 进展类文档每项写状态、与计划的差异、原因、下一步；状态用一套固定的词，如"已完成 / 按期 / 有风险 / 延期"，全文统一；不在正文里解释这套词。已完成的事项，下一步写"无"。
- 坏消息和好消息用同样的位置和篇幅写。
- 每个数字写出比较对象：与计划比、与上期比，或与目标比。
- 选项之间用同一组维度比较，写成对比表。
- 作者的推荐与事实分开写，推荐标明是推荐。

## 要读的内容块

- `blocks/figure-table.md`：有数据或选项对比时读。
- `blocks/citation.md`：依据来自外部资料时读。

## 审查清单

- [ ] 第一段写了结论和请求（或"无需决定"），有截止时间时写了截止时间。
- [ ] 每个数字都有比较对象。
- [ ] 状态词全文只用一套。
- [ ] 有选项时，每个选项写了代价、收益、风险，并给了推荐和理由。
- [ ] 每个未决事项写了由谁、何时弄清。
