# 文档计划、文档外包需求

## 适用

- 读者：
  - 文档计划：信息开发负责人（管理者）及其委派的人，用它确认文档项目做什么、谁来做、何时交、怎么验收。计划还要给项目经理、产品经理、评审人和高层管理者看。
  - 文档外包需求：采购经理与审批人、供应方的建议书作者，用它报价、谈判和验收。这类读者熟悉采购和供应协议，采购的基础概念直接使用。
- 用在：
  - 用户文档项目的文档计划，敏捷和传统项目都适用。
  - 向外部供应方或公司内另一部门委托文档或翻译工作时的需求说明、工作说明、征求建议书和验收条款；供应方回复的建议书只给章节目次。
- 不适用：
  - 文档本身（手册、帮助、安全须知）→ `user-manual.md`
  - 教程、快速入门、操作指南 → `tutorial.md`
  - API 参考 → `api-reference.md`
  - 软件产品本身的需求规格、PRD → `requirements.md`
  - 软件测试计划、测试报告 → `test-docs.md`
  - 文档以外的项目计划、配置管理计划和其他开发过程文档 → `lifecycle-other.md`
  - 文档风格指南、术语表本身 → `lifecycle-other.md`
  - 文档项目的结项总结 → `lifecycle-other.md`
  - 外包合同的法律条款（违约、付款争议、责任上限、争议解决）：本文件不管，由法务定稿，写 `【待补：法务确认××条款】`。

## 必需章节

### 文档计划

标题直接用下列章节名，属于 base 允许的固定标题。第 3–16 项按 26511 7.2.1–7.2.14 的目次排列，第 17–20 项取自 26511 其他条款，第 1、2 项是作者判断。某项不适用时保留标题，写一句不适用的理由。

1. **计划信息**：计划版本、日期、编写人、批准人。
2. **摘要**：交付物、发布日期、总成本、需要批准人决定的事项及截止日期，不超过 5 句。
3. **目标**：这批文档要帮用户完成什么、要解决的现有问题（如支持工单多、上手慢）。
4. **范围**：覆盖的产品、版本、功能模块和平台；写明不在范围内的内容。
5. **文档的目标用户**：每类用户的任务、经验和使用场景。这里写的是用户文档的使用者，不是读这份计划的人；后者按 base 写进交付说明。
6. **主题清单**：要编写的全部主题，按写作规则里的表格列出。
7. **复用策略**：哪些主题在多个交付物或多个产品间共用、用什么机制复用（单源、片段引用、条件文本）。
8. **无障碍要求**：交付物要满足的无障碍要求和对应标准。
9. **翻译与本地化**：目标语言、各语言的交付时间点、各语言的交付物、术语表由谁维护。不翻译时写明。
10. **交付物**：逐项列出交付物，每项写明形式（在线帮助、PDF、印刷件、界面内嵌文字、视频）、所属发布版本和交付渠道。
11. **工具**：写作、构建、发布、翻译管理和版本控制所用的工具及版本。
12. **质量、评审与测试**：每个交付物的评审类型、评审人、评审轮次、最终批准人（姓名或岗位）；是否做可用性测试，由谁做。
13. **进度**：进度表每行一个交付物，列为各里程碑的完成日期；或者先列工作分解结构（WBS，每个交付物下分工作包），再给里程碑表。里程碑用产品里程碑的名称，第一个文档里程碑排在产品设计阶段结束之前。
14. **工时与成本估算**：按人工、非人工，以及翻译、印刷和发布费用三类分列小计，写明每类的估算依据。
15. **风险**：每条风险写触发条件、影响和应对办法。
16. **团队**：成员、角色和职责；写明信息开发人员缺位时由信息开发负责人指定替补。
17. **维护与变更**：版本控制与归档方式、内容的长期生命周期策略（何时修订、何时下线）、范围变更的审批人和审批流程，以及触发重新估算的事件（如新增功能、新增语言、发布日期提前）。
18. **度量**（可选：组织要求跟踪质量或效率时加）：选用的指标和采集方式，如质量缺陷数、用户满意度、用户反馈、复用率、返工量、周期时间。
19. **沟通**（可选：干系人多于一个团队时加）：向谁、以什么频率、用什么形式报告进度，含向高层管理者的报告。
20. **外包**（可选：任何部分交给外部或其他部门做时加）：外包哪部分，指向单独的外包需求文件。

### 文档外包需求（采购方发出）

标题直接用下列章节名，属于 base 允许的固定标题。直接委托某家供应方、不招标时，省去第 9、10 项。

1. **项目目标**：采购这批文档要达到的目的。
2. **采购的服务**：从这些环节里勾选：信息管理、信息设计与开发、编辑与评审协调、信息测试（含可用性测试）、翻译与本地化、生产与实物包装、分发与交付、工具选型与实施建议、过程改进。与本次交付物有关、但没勾选的环节，写明由谁负责。
3. **信息产品规格**：要交付的信息是什么、给哪类读者；读者和交付物从文档计划摘录。媒介不写在这里，写进第 8 项交付物清单。
4. **需求与约束**：逐项写进度约束；可用性（usability，读者用起来顺不顺）；产品改版时的修改要求；本地化与翻译；法律；安全（人身与设备安全，如安全警示）；信息安全（供应方接触采购方资料和系统时的要求，源文件归属见第 11 项）；要遵循的标准和风格规范；质量管理要求。
5. **工作说明**：供应方要做的工作和不做的工作、采购方提供的资料、样机、专家和评审时间。
6. **工作量基数与报价要求**：源文档的字数、主题数、图片数和源格式；报价单位（按字、按页或按人天）和报价表格式；付款节点与验收挂钩。
7. **支持过程要求**：进度报告的频率和形式、变更控制流程、评审流程、配置管理。
8. **交付物清单**：逐项写名称、格式和媒介、源文件是否交付、语言、交付日期。
9. **供应方能力与经验、投标须知**：要求供应方证明的能力、类似项目经验；建议书提交方式和截止日期。
10. **建议书评审准则**：评分项和权重，与第 4 项的需求一一对应。
11. **保密与知识产权**：源文件、译文、术语库、翻译记忆库的归属和使用范围。归属写采购方的意图，条款措辞由法务确认。
12. **验收条款**：验收的对象、标准、方法、负责人、期限，不通过时的返工次数和期限；采购方逾期未给结论时的处理（如视为通过，由法务确认）；验收后的质保期和期内的修改责任。
13. **收尾**（可选：长期项目或多批交付时加）：结项时移交的资料、账号和工具许可的回收。

### 建议书（供应方发出）

按 26512 第 11 章的目次列章节：对需求的理解、项目范围、过程、经验能力与资源、进度、交付物、报价。

## 写作规则

- 先判定写的是哪一份：项目内部的文档计划，还是发给供应方的外包需求。两者都要时，拆成两份文件。外包需求是发给外部的独立文件：读者、交付物、进度从文档计划摘出供应方需要的部分，写进正文或附件；成本、风险、团队三节只留在内部计划里。

### 文档计划

- 已有其他文件写过的内容（用户需求评估、风格指南、术语表），在计划里写文件名和位置，只摘结论。
- 本文件里的表格按 `blocks/figure-table.md` 写，规划阶段未定的格子写 `【待补】`。
- 主题清单用表格，每行一个主题，列出主题名、作者、所属交付物、使用位置、源文件名、状态。主题多于 30 个时，完整清单另放表格文件，计划里写位置和几行样例；规划阶段未定的作者和源文件名留 `【待补】`。
- 引用标准、风格指南等文件时，来源和版本按 `blocks/citation.md` 写。
- 计划要求受控语言时，写 ASD-STE100 Simplified Technical English Issue 9（2025-01-15），与 base.md 一致。26511 3.1.28 注里的 Standard Technical English、Issue 6（2013）已过时，只在说明历史时提及。
- 计划引用文档项目管理标准时，写 ISO/IEC/IEEE 26511:2018。GB/T 16680-2015 采用的是已撤销的 2011 版，只在说明国标沿革时提及。

### 敏捷项目里的文档计划

- 写明每类交付物用敏捷方式还是其他方式开发，如在线帮助跟随迭代、印刷手册按发布节点。
- 把"本迭代功能的用户文档已写完并评审"写进完成定义或发布验收标准。
- 分两层计划：整个项目的范围和里程碑，加上每个迭代的文档工作量估算和人手。
- 写出发布前临近截止的内容变更怎么处理：由谁批准、最晚接受到哪天。
- 进度跟踪写明用什么方式，如燃尽图、站会。
- 由非专职人员兼写时，计划里安排培训，并增加一轮同行评审。

### 文档外包需求

- 对外委托时称"采购方""供应方"，开头写明双方全称，全文不用"你""我们""甲方""乙方""我司"。这里不按 base 用"你"称呼读者，因为这份文件约束的是双方。委托方是公司内另一部门时，称"委托方"和"承接方"，同样写需求、交付物和验收条款。
- 需求与约束写成与媒介无关的要求，媒介写进交付物清单；有印刷件时单列包装要求。
- 要求供应方按某项标准交付时，把标准编号和年份写进合同条款。多个供应方共同交付时，给标准要求的每项活动指定负责方。
- 允许裁剪标准要求时，在合同里列出裁剪的条款和理由。
- 引用 26512 时用 2026 版的条款号。用户的模板引用 26512:2018 附录 A、B 的检查表时，注明该版已撤销，2026 版目次里已没有这两个附录。
- 外包翻译时，单列翻译供应方的选择条件、翻译评审与质量控制方式、术语表的提供方。
- 每条验收标准写成可判定的条件，如"抽查 20 个主题，每个主题的操作步骤在 【待补：版本号】 上逐条实测无误"。
- 敏捷交付时，按迭代分批验收，每批验收该迭代功能对应的用户文档。

## 审查清单

### 文档计划

- [ ] 开头有计划信息（版本、日期、编写人、批准人）和摘要，摘要写了待批事项和截止日期。
- [ ] 第 1–17 项都有标题；不适用的项写了理由。
- [ ] 范围一节列出了不在范围内的内容。
- [ ] 目标用户一节每类用户都写了任务、经验和使用场景。
- [ ] 主题清单（正文或指向的表格）每行都有作者、所属交付物、使用位置和源文件名，未定的写了 `【待补】`。
- [ ] 复用策略、无障碍、翻译与本地化三项各写了"做"或"不做"，"不做"的写了理由。
- [ ] 交付物清单每项都写了形式、所属发布版本和交付渠道。
- [ ] 每个交付物都有评审人和最终批准人。
- [ ] 进度表里每个交付物都有各里程碑的完成日期，里程碑用产品里程碑的名称。
- [ ] 成本估算按人工、非人工，以及翻译、印刷和发布三类列了小计和估算依据。
- [ ] 每条风险都写了触发条件、影响和应对办法。
- [ ] 团队一节写了信息开发人员缺位时的替补。
- [ ] 维护一节写了版本控制方式、内容下线条件、范围变更的审批人和触发重新估算的事件。
- [ ] 敏捷项目：用户文档写进了完成定义或发布验收标准。
- [ ] 敏捷项目：写了临近发布的内容变更由谁批准、最晚接受日期。
- [ ] 引用的标准写的是 26511:2018，GB/T 16680-2015 只出现在说明国标沿革的地方。
- [ ] 提到 STE 时写的是 Simplified Technical English Issue 9。
- [ ] 计划里的表格通过了 `blocks/figure-table.md` 的审查清单（未定的格子写 `【待补】` 的除外）。

### 文档外包需求

- [ ] 开头写明了双方全称，全文称"采购方""供应方"（内部委托称"委托方""承接方"）。
- [ ] 第 1–12 项都有标题；直接委托时省去了第 9、10 项。
- [ ] 写明了采购哪些服务环节；未采购的环节中，与本次交付物有关的写了负责方。
- [ ] 读者、交付物、进度写在正文或附件里，没有只写"见文档计划"，也没有带上内部计划的成本、风险、团队三节。
- [ ] 需求与约束逐项覆盖进度、可用性、改版、本地化与翻译、法律、安全、信息安全、标准与风格规范、质量管理，不适用的写明。
- [ ] 工作说明列了采购方提供的资料和供应方不做的工作。
- [ ] 写了源文档规模和统一的报价单位。
- [ ] 写了进度报告频率和变更控制流程。
- [ ] 交付物清单每项有格式和媒介、语言、交付日期，并写明源文件是否交付。
- [ ] 写了源文件、译文、术语库、翻译记忆库的知识产权归属。
- [ ] 招标时有建议书评审准则，评分项对得上需求项。
- [ ] 每条验收标准都能判定通过或不通过，写了验收负责人、期限、返工规则、逾期处理和质保期。
- [ ] 外包翻译时写了翻译供应方选择条件、质量控制方式和术语表提供方。
- [ ] 敏捷交付时按迭代分批验收。
- [ ] 要求按某标准交付时，合同条款写了标准编号和年份；多供应方时每项必需活动都有负责方。
- [ ] 引用 26512 的条款号来自 2026 版；引用 2018 版附录 A、B 的地方注明了该版已撤销。
- [ ] 违约、责任、争议解决这类法律条款写成了 `【待补：法务确认……】`。

### 建议书

- [ ] 逐条回应了外包需求里的需求与约束。
- [ ] 报价按采购方给的报价单位和报价表格式。

## 示例

改写前（外包需求里的验收条款）：

```markdown
## 验收
供应方交付的文档应质量良好、符合我方要求，经我方确认后验收。
```

改写后：

```markdown
## 验收条款
交付物按以下条款验收：
- 对象：交付物清单第 1–4 项的中英文 HTML 和 DITA 源文件。
- 标准：术语与附件 B 术语表一致；抽查 20 个主题，操作步骤在 【待补：版本号】 上逐条实测无误。
- 负责人：采购方产品文档组 【待补：姓名】，收到交付物后 10 个工作日内给出结论。
- 不通过：供应方 5 个工作日内返工，同一交付物最多返工 2 次。
```
