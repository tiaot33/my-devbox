# 其他开发过程文档

## 适用

- 读者：项目内外要据文档做决策或干活的人。按 GB/T 8567 的角色划分：
  - 管理人员：可行性分析报告、开发计划、配置管理计划、质量保证计划、开发进度月报、项目开发总结报告。
  - 开发人员：可行性分析报告、开发计划。
  - 用户：软件产品规格说明、软件版本说明。软件产品规格说明也是该软件的基本支持文档，维护人员也读。
- 用在：路由表里没有专门文件的开发过程文档。先按下表判定它属于 15289 的哪种通用类型（计划、规程、报告、请求、描述、规格、策略），或属于记录。CONTRIBUTING、行为准则这两类仓库规范文件，按策略或规程处理。
- 不适用：
  - 需求规格、PRD、接口需求 → `requirements.md`
  - 架构描述 → `architecture.md`；单条 ADR → `domain-modeling` skill
  - 模块、接口、数据库设计说明 → `design.md`
  - 测试计划、测试说明、测试规程、测试报告，以及测试中发现的缺陷报告（测试事件报告）→ `test-docs.md`
  - 文档计划、文档外包需求 → `doc-plan.md`
  - 用户手册、操作手册 → `user-manual.md`；编程手册、SDK 文档 → `api-reference.md`
  - 面向公众、客户的版本发布公告、更新说明 → `public-notice.md`。随交付物给需方、运维、维护人员的软件版本说明留在本文件。
  - CHANGELOG → `base.md`（本 skill 未收录，在交付说明里告诉用户）
  - 线上事件的复盘（事后原因分析、整改措施）→ `base.md`
  - Agent 给用户的结果汇报 → `agent-report.md`；对外发表的科技报告 → `tech-report.md`

| 类型 | 判定要点 | 常见文档（中文名为本文译法） |
| --- | --- | --- |
| 计划 | 达成既定目的的系统性行动方案，写明何时、如何、由谁做 | 软件开发计划、安装计划、移交计划、配置管理计划、质量保证计划、项目管理计划 |
| 规程 | 执行过程、活动或任务的有序步骤；是组织批准的做法 | 发布规程、值班规程、生命周期规程 |
| 报告 | 调查、观察、评估、测试这几类活动的结果 | 可行性分析报告、开发进度月报、项目开发总结报告、进展报告、评估报告 |
| 请求 | 发起一项既定行动或变更，以满足某个需要 | 变更请求、资源请求、风险行动请求 |
| 描述 | 表示计划中或实际存在的概念、功能、设计或对象 | 运行概念说明、软件版本说明、过程描述 |
| 规格 | 完整、精确、可验证地给出需求、设计、行为或其他特性 | 软件产品规格说明 |
| 策略 | 清晰、可度量地表达组织的偏好方向，用来约束决策 | 生命周期策略、质量管理策略 |
| 记录 | 作为一个单元处理的一组相关数据项；15289 把它单列在第 9 章，不属于第 7 章的通用类型 | 登记表、台账中的一条 |

GB/T 8567 里由本文件兜底的文档归类如下：计划（软件开发计划 7.2、软件安装计划 7.4、软件移交计划 7.5、软件配置管理计划 7.17、软件质量保证计划 7.18）、报告（可行性分析报告 7.1、开发进度月报 7.19、项目开发总结报告 7.20）、描述（运行概念说明 7.6、软件版本说明 7.22）、规格（软件产品规格说明 7.21）。

## 必需章节

记录以外的类型都用下面的骨架，记录的写法见"写作规则 / 记录"。章名沿用 GB/T 8567 第 7 章各文档共有的写法。

标题下、第 1 章之前写 1～3 句导语，不编章号，写结论或读者要做的事：规程写批准人、文档版本号和生效日期；请求用两句分别写要发起的行动或变更、它要满足的需要；报告写主要结果。

1. **引言**：
   - 标识：文档适用的系统和软件的完整标识：标识号、标题、版本号；有缩略词、发行号时也写。
   - 系统概述：系统用途和一般性质；开发、运行、维护的历史；投资方、需方、用户、开发方、支持机构；当前和计划的运行现场。只写读者完成本文任务需要的子项，与读者的决策无关的删掉，在文档概述里写明删了哪些。
   - 文档概述：本文档的用途和内容，以及使用本文档时的保密性和私密性要求；没有这类要求时写"无"。
   - 组织和职责、资源（计划类写）：质量保证计划、配置管理计划设为引言 1.4、1.5，推广到其他计划为作者判断。
2. **引用文件**：每份引用文档写编号、标题、修订版本和日期；没有编号的在线文档写链接和访问日期或页面更新日期；不能从正常渠道拿到的，写出获取来源。没有引用文件时该章写"无"。
3. **正文**：按类型写，见下表。
4. **注解**：理解本文档所需的背景和原理、术语和定义、正文用到的全部缩略语的字母序列表。缩略语表比 `base.md` 严：包括 `base.md` 允许不展开的通用缩写；正文首次出现处仍按 `base.md` 处理。没有缩略语时写"无"。
5. **附录**（可选：有为便于维护而单独出版的图表、分类数据时加）：按 A、B、C 编号，可单独装订。

| 类型 | 正文必含 |
| --- | --- |
| 计划 | 每项活动的负责人、时间、方法；日程表（放正文最后一章） |
| 规程 | 编号的有序步骤 |
| 报告 | 所做的活动、得到的结果；有计划时，与计划的对比和偏差原因 |
| 请求 | 要发起的行动或变更；它要满足的需要 |
| 描述 | 被描述的对象；它是计划中的还是已存在的 |
| 规格 | 每条特性及其验证方法；需求的可追踪性（产品规格说明单设一章） |
| 策略 | 每条可判定是否遵守的陈述；它约束哪类决策 |

## 写作规则

### 引用标准

- 写 GB/T 8567-2006。"GB 8567-88"是已被代替的 1988 版，"GB/T 8567-2016"不存在。说明旧版时写"已被 GB/T 8567-2006 代替"，不写具体废止日，因为两处一手记录的日期不一致。
- 只写 15289 本身的条款号；需要 12207、15288 的条款时，到现行版（12207:2026、15288:2023）查。15289 第 8 章映射的是已被替代的 12207:2017 和 15288:2015。
- 写"参照 ISO/IEC/IEEE 15289:2019 组织"。为组织或项目声明"符合"时，要有组织文件、项目计划或合同记录对记录和信息项的剪裁，而本文件的章节没有逐条对过第 7 章。第 7 章的内容写"参照第 7 章"，条款号只写本文件已列出的。

### 剪裁与取舍

- 一份文档混了两类（如计划里夹着上期结果）时，两类内容分章写，或拆成两份。
- 用户点名 GB/T 8567 时，沿用其章条标题，需要时往下细分，不需要的条合并或删掉并重新编号。用户点名 15289 时，章名和文档名可以改，可以增加或合并。两种情况都在文档概述里用一句话写出改了什么，如"按 GB/T 8567-2006 7.18 排章，合并第 7、8 章"。只套本文件通用骨架时，不写剪裁说明。
- 大项目把计划拆成子计划：开发计划可分出质量保证、配置管理、用户培训、安装实施计划。拆出去的部分在主计划里写一句，并引用子计划的编号和版本。
- 可选条目在提纲阶段标"（若适用）"或"（若有）"，成稿时去掉标记，保留或删除该条。

### 重复与引用

- 本文读者与被引文档的读者属同一角色、且手头有被引文档时，写引用：编号、版本和章条号。15289 的"包含"既指信息写在文中，也指给出指向它的引用。
- 本文读者是别的角色、或拿不到被引文档时，在本文引言里重写系统的功能、性能、输入和输出、设备。措辞、术语和详略按本文读者调整。
- 涉及安全使用、信息安全、个人敏感信息保护的内容在本文写全，不只给引用。15289 把这类信息定为关键信息，"完整"以含全关键信息为前提。

### 计划

- 每项活动落到具体角色和日期，并写出产出物。

### 规程

- 步骤从 1 起编号，按执行顺序排。分阶段写时用子节标题分组，步骤号全文连续；子节标题按 `base.md` 写成陈述句或问题，如"发布失败时回滚到上一版本"。
- 有分支时写明判断条件和跳转到的全文步骤号。
- 未经组织批准的规程在标题末尾加"（草案）"，导语里不写批准人。

### 报告

- 进度月报、总结报告里，进度、资源、经费各项都与计划对比。进度用"提前 / 按期 / 推迟"，资源用"超出 / 一致 / 不足"；经费沿用资源那组词。不一致的写原因和措施。
- 对比写成"计划值、实际值、状态"三栏表格。
- 阶段开始或结束时，写出阶段名称和日期。
- 月报末尾写下个月的工作计划和本月重要问题的建议。
- 总结报告里，每项功能和性能对照可行性分析报告、开发计划和需求说明，写"达到 / 未完全达到 / 超过"；风险写初期预计、实际发生、消除情况；缺陷按评审和测试阶段分列。
- 可行性报告至少给两种可选方案，并写出选定最终方案的准则。

### 请求

- 服务请求是针对信息或风险已预先评估过的常规变更或规程的请求。写服务请求时，只写请求的变更、引用的预评估规程编号和执行时间，不重做评估。

### 描述

- 同一份里既有计划中的对象、又有已存在的对象时，分节标明。
- 版本说明写出自上一版本以来的全部变更；每个已知问题写如何识别，以及避免、更正或处理的办法。
- 版本说明的清单条目写全标识号、标题、缩略语、日期、版本号、发行号。

### 规格

- 产品规格说明单设"合格性规定"一章，写怎么证明交付物是该软件的有效拷贝。

### 策略

- 每条写明适用于谁。"重视代码质量"改成"合入主干的变更必须有一名非作者批准"。

### 记录

- 用表格或固定字段写，一条记录只记一件事；字段名全表统一。目的、范围、摘要这类文档要素放在登记表的说明里，不放进每条记录。

## 审查清单

- [ ] 引言的标识写了标识号、标题、版本号；有缩略词、发行号时也写了。
- [ ] 引言有系统概述和文档概述；系统概述删掉的子项在文档概述里写明了。
- [ ] 文档概述写了保密性和私密性要求，没有时写"无"。
- [ ] 引用文件每条有编号、标题、修订版本和日期，在线文档有链接和日期；没有引用文件时该章写"无"。
- [ ] 注解列出了正文用到的全部缩略语，按字母序；没有缩略语时写"无"。
- [ ] 用户点名 GB/T 8567 或 15289 时，文档概述写明了做过的剪裁。
- [ ] 没有"GB 8567-88""GB/T 8567-2016"，也没有转引 15289 第 8 章里的 12207、15288 条款号。
- [ ] 没有写"符合 15289"，也没有第 7 章的具体条号。
- [ ] 安全使用、信息安全、个人信息相关内容在本文写全，没有只给引用。
- [ ] 用引用代替重抄的地方，写了被引文档的编号、版本和章条号。
- [ ] 计划：每项活动都有负责人、时间、方法；有日程表，放在正文最后一章。
- [ ] 计划：拆出的子计划在主计划里有编号和版本。
- [ ] 规程：步骤号全文连续，每个分支有判断条件和跳转步骤号。
- [ ] 规程：导语写了批准人、文档版本号和生效日期；未批准的标题末尾有"（草案）"。
- [ ] 月报、总结报告：进度、资源、经费各项有计划值、实际值、状态，状态只用固定词；每项偏差写了原因和措施。
- [ ] 总结报告：每项功能和性能写了"达到 / 未完全达到 / 超过"之一。
- [ ] 可行性报告：至少两种可选方案，写了选定准则。
- [ ] 请求：导语用两句分别写了要做的行动或变更和要满足的需要。
- [ ] 描述：写明了对象是计划中的还是已存在的。
- [ ] 版本说明：列了上一版本以来的全部变更；每个已知问题有处理办法；每个清单条目有标识号、标题、缩略语、日期、版本号、发行号。
- [ ] 规格：每条特性有验证方法；有需求的可追踪性。
- [ ] 策略：每条陈述都能判断是否遵守，并写了约束的决策范围和适用对象。
- [ ] 记录：每条只记一件事，字段名统一。
- [ ] 成稿里没有残留"（若适用）""（若有）"标记。

## 示例

改写前（开发进度月报的一段）：

```markdown
本月进展顺利，完成了大部分开发任务，预计下月可以按时进入测试。
人力投入略有增加，经费正常。
```

改写后：

```markdown
| 项 | 计划值 | 实际值 | 状态 | 原因与措施 |
| --- | --- | --- | --- | --- |
| 编码阶段结束 | 2026-10-15 | 2026-10-22 | 推迟 | 支付接口联调返工；已加 1 人 |
| 工时 | 320 人时 | 368 人时 | 超出 | 同上；11 月计划扣回 24 人时 |
| 经费 | 4.0 万元 | 4.0 万元 | 一致 | — |
```
