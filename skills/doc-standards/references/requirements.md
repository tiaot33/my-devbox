# 需求规格说明、PRD

## 适用

- 读者：
  - 业务需求（BRS）、利益相关方需求（StRS）、PRD：业务方和用户代表，确认写下的需求是不是他们要的系统。
  - 系统需求（SyRS）、软件需求（SRS）：设计人员据此设计，测试人员据此测试；顾客和供方据此达成一致。
- 用在：BRS、StRS、SyRS、SRS、PRD 的编写、改写、评审；需求条目库里单条需求的编写和评审。
- 不适用：
  - 模块划分、数据结构、模块间信息流和控制流 → `design.md`
  - 系统由哪些部分组成、各视图 → `architecture.md`
  - 测试计划、测试用例、测试报告 → `test-docs.md`
  - 项目需求：成本、交付进度、报告规程、开发方法、质量保证、验证和确认准则、验收规程 → `lifecycle-other.md`
  - 单独成册的运行概念说明（OpsCon、ConOps）→ `lifecycle-other.md`
  - 文档外包需求 → `doc-plan.md`

## 必需章节

先按下表定类型，再按对应小节搭章节：

| 类型 | 写谁的需求 | 典型内容 |
| --- | --- | --- |
| BRS 业务需求 | 组织为什么要这个系统 | 业务目的、使命与目标、业务模型、业务过程、高层运行场景 |
| StRS 利益相关方需求 | 用户和其他利益相关方要什么 | 利益相关方、运行概念、运行场景、用户需求 |
| SyRS 系统需求 | 整个系统应做到什么 | 功能、性能、接口、模式和状态、物理与环境条件 |
| SRS 软件需求 | 软件部分应做到什么 | 产品功能、用户特点、外部接口、性能、设计约束 |
| PRD 产品需求文档 | 一个产品或功能为什么做、给谁、做什么 | 无标准；按下文"PRD"一节组织 |

- 交给开发和测试、作为验收基线的，写 SRS 或 SyRS；用于产品评审、确定范围的，写 PRD；用户只说"写个需求文档"又判断不出时，问用户。

章节顺序和标题按下面处理：

- 标识与前置信息放在文档首部。SRS 把定义、缩略语和引用文件放进引言；PRD 正文从"背景与目标"开始，定义、引用文件、待定项清单、修订记录放在文末或附录。
- 下列条目名可以直接作章名，算 base.md 所说的"类型文件规定的固定标题"；也可以合并或改名。每个条目都要有对应内容，不适用时写一句原因。
- base.md 清单里的"开头一段"，在 PRD 指"背景与目标"的首段，在 SRS 指"范围"。

所有类型共有：

1. **标识与前置信息**：文档名称、版本、日期。
2. **修订记录**：按 `blocks/revision.md` 写；"改了什么"列出改了哪些需求编号，批准人必写；首版和未批准的草稿也写一行，批准人写"未批准"。
3. **定义与缩略语**：多义术语和产品特征的唯一叫法在这里定义。
4. **引用文件**：每份文件写名称、编号、日期、出版组织、获取来源。
5. **待定项清单**（可选：有待定项时加）：见"写作规则 · 需求集"。

### SRS

6. **引言**：
   - 目的：写明这份 SRS 给谁读。
   - 范围：写产品名称、做什么和不做什么、收益和目标。
7. **总体描述**：只写影响需求的一般因素，不写具体需求。
   - 产品描述：产品在更大系统中的位置，配框图；系统、用户、硬件、软件、通信接口。
   - 产品功能概要。
   - 用户特点：教育程度、经验、专业技能，并说明它们导致了"具体需求"一章的哪些需求。
   - 约束、假设和依赖。
   - 需求分配：哪些需求推迟到将来版本。
8. **具体需求**：外部接口；功能；易用性（usability）；性能；逻辑数据库；设计约束；标准符合性；软件系统属性，即可靠性、可用性（availability）、安全保密性、可维护性、可移植性。
   - 外部接口逐项写：名称、目的、输入来源或输出去向、有效范围和精度、单位、定时、数据或命令格式。
   - 从系统模式、用户类型、对象、特征、激励、响应、功能层次中选一种作为本章的组织方式，在章首写明。
9. **验证**：每条需求的验证方法，可做成"需求编号—验证方法"对照表。
10. **支持信息**：附录、索引；写明附录是否属于需求。

### SyRS

6. **系统需求**：
   - 概述：系统目的；系统范围；系统概述。
   - 需求：功能；易用性；性能；系统接口；系统运行；模式和状态；物理特性；环境条件；系统安全保密；信息管理；政策和法规；生存周期保障；包装、搬运、装运和运输。
   - 收尾：验证；假设和依赖。

### StRS

6. **利益相关方需求**：
   - 概述：利益相关方的目的；利益相关方的范围；概述。
   - 背景：利益相关方；业务环境；使命和目标；业务模型；信息环境。
   - 系统运行：系统过程；运行策略和规则；运行约束；运行模式和状态；运行质量。
   - 需求与概念：用户需求；运行概念；运行场景；拟建系统的其他详细概念；项目约束。

### BRS

6. **业务需求**：
   - 概述：业务目的；业务范围；概述。
   - 背景：主要利益相关方；业务环境；使命和目标；业务模型；信息环境。
   - 业务运行：业务过程；运行策略和规则；运行约束；运行模式；运行质量；业务结构。
   - 高层概念：高层运行概念；高层运行场景；其他高层生存周期概念；项目约束。

### PRD

PRD 不在 29148 和 GB/T 9385 的范围内。下面的章节按 29148 中最接近的 BRS、StRS 条目映射，各条写法都是作者判断。排期和里程碑写进项目计划（`lifecycle-other.md`），PRD 里只放链接。

6. **背景与目标**：要解决的业务问题；每个目标写指标和目标值。
7. **用户与场景**：目标用户及其特点、典型使用场景；用户故事（"作为……我想要……以便……"）放在这里。
8. **范围**：本版本做什么、明确不做什么、推迟到哪个版本。
9. **需求**：按功能或用户流程分组，在章首写明分组方式。每条按本文件的单条需求规则写，来自用户故事的需求也改写成 EARS 句式；验收标准写进该需求的"验证成功准则"属性。
10. **约束、假设和依赖**。

## 写作规则

### 与 base.md 的差异

- 需求文档全文用下面四个情态词，替代 base.md 的"必须""不得""可以"一套，引言、假设、约束这类非需求句也照此写；按 base.md 清单自查时，情态词一条按本节判定：
  - 应：义务。有约束力的需求句只用"应"。
  - 不得：禁止。只在无法正面写时用，并写出系统此时的正向响应；不写"不应"。
  - 可以：许可。
  - 宜：目标或期望。base.md 不设这一级，需求文档保留它；目标单独成节，或在属性里标为"目标"。
- 需求文档不用"你"称呼读者，写系统名或角色名。
- 需求句按描述句计数，上限 40 字；超过时把状态条件拆成"条件 / 结果"表格，或拆成多条需求。

### 单条需求的句式

- 每条需求按"状态条件 → 触发事件 → 系统名 → 应 → 系统响应"的固定顺序写；状态条件可以没有或有多个，触发事件最多一个，系统名恰好一个。
- 每条只写一个系统响应；要写两个动作时拆成两条需求。
- 按需求类型选句式：

| EARS 句式 | 中文写法 |
| --- | --- |
| 通用（始终生效） | `<系统>应<响应>。` |
| 状态驱动 While | `在<状态>期间，<系统>应<响应>。` |
| 事件驱动 When | `当<触发事件>时，<系统>应<响应>。` |
| 可选特性 Where | `对于具备<特性>的<产品>，<系统>应<响应>。` |
| 不期望行为 If-then | `若<异常情形>，则<系统>应<响应>。` |
| 组合 | `在<状态>期间，当<触发事件>时，<系统>应<响应>。` |

- 写系统响应动作的需求时，先找出它的适用条件，有条件的写成状态、事件或不期望行为句式；通用句式只留给无条件成立的需求，如质量、尺寸。
- 每写一条事件驱动需求，就检查无效输入、超时、失效这几种情形，逐一补写"若……则……"需求；判断不需要时，在工作记录里写一句原因，不写进正文。
- 系统名写负责的系统或部件。用户界面需求写成系统行为，或写成可测的用户绩效，如"退款登记界面应使经过 1 h 培训的客服人员在 3 min 内完成一次退款登记"。
- "应"后面不加"能够""具备……的能力""可以"：写"系统应导出……"。
- 把"以便……""为了……"这类目的说明移到理由属性里，需求句只写要求。
- 括号里的补充说明拆成单独子句或单独需求。
- 写外部可观察的行为；只有当某个设计确实受约束时才写成设计约束，并在理由属性里写出约束来源。
- 可维护性等软件系统属性写成需求时，给出可验证的指标；给不出指标、只是良好设计实践的，从需求里删掉。

### 让需求可验证

- 每个量都写数值、单位和范围或容差，如"在 95% 的请求中 2 s 内返回"，不写"快速响应"。
- 把不可测量的形容词、副词换成数值或可列举的条件。常见的有：友好、足够、适当、高效、灵活、若干、大约、较多、快速、良好、稳定、可靠、及时、合理；这份词表只是示例。
- 把"尽可能""在可行时""必要时""视情况"换成明确的条件，或删掉。
- 把"包括但不限于"换成完整列举。
- 把"始终""永不""100%""所有"换成可达到的指标；表示全称时用"每个"。
- 把"最终""之后""立即""同时"换成具体时限或先后条件。
- 每条需求单独读也能懂：不依赖标题或上一条需求；指向本条以外的内容时写出名词，不用"它""该""此""上述"。同一句里已出现的名词，可以用"这个 X"回指。比 base.md 更严：指代唯一也要写出名词。
- 设计不出验证方法的需求，改写到能验证，或删掉。

### 需求集

- 一份需求文档只写一个实体（一个系统、子系统或软件）的需求。
- SRS 属于更大的系统时，写出系统与软件之间的接口，需求编号追溯到上层 SyRS。
- 每条需求给一个唯一编号，如 `REQ-AUTH-003`。
- 同一需求只写一处，其他位置引用编号；确需重复时附交叉索引表。
- 用需求表或条目块给每条需求附属性，按类型选属性集；拿不到的属性值填"未定"，不进待定项清单：
  - StRS、BRS、PRD 至少附 5 项：编号、理由、上级或来源追溯、优先级、验证方法。
  - SyRS、SRS 附下表的 16 项。

| 属性组 | 属性 |
| --- | --- |
| 标识与归属 | 编号（A15）、作者（A17）、负责人（A19） |
| 理由与追溯 | 理由（A1）、上级追溯（A2）、来源追溯（A3）、分配（A5） |
| 验证 | 验证成功准则（A6）、验证策略（A7）、验证方法（A8）、验证责任方（A9）、验证状态（A28）、确认状态（A29） |
| 管理 | 优先级（A34）、关键性（A35）、实现风险（A36） |

- 优先级的取值沿用项目约定，没有约定时填"未定"。关键性取"基本的""有条件的""可选的"三级之一，GB/T 9385 称之为"重要性"；需要标稳定性时，写预期变更次数。
- 验证方法取检查、分析、演示、测试之一。
- 追溯的写法见 `blocks/traceability.md`。向上的来源可以是 StRS 条目、法规、上层需求，向下是分配到的部件或下层需求。
- 需求里的名词与术语表、数据字典、架构模型里的叫法一致。
- 用图、伪码、状态机或决策表表达需求时，保留一段自然语言描述，让不熟悉符号的读者也能读懂；复杂行为在需求里引用图或接口控制文件的编号。
- 待定项分两层写：
  - 正文行内只写 `【待补：TBD-n】`。
  - 待定项清单写成表，列为编号、缺什么、原因、由谁确定、措施、关闭日期；由谁确定还不知道时填"未定"。
  - 只有影响需求内容的缺口进清单；作者、链接这类元数据缺口照 SKILL.md 写 `【待补：缺什么】`。

### 审查需求

- 结果分两部分报告：需求验证（单条和整体是否符合本文件规则）和需求确认（是否反映了利益相关方要的系统）。
- 需求确认要由利益相关方参与；agent 只完成需求验证，确认部分写 `【待补：请 <利益相关方> 确认需求是否符合实际需要】`。
- 检查与上层文档的一致性，以及三类内部矛盾：同一对象的特征矛盾、行为的逻辑或时间冲突、同一对象用了不同术语。

### 英文需求

- 需求用 shall，目标用 should；这与 base.md"英文文档"一节的 must 不同。
- EARS 关键词按原文写：While、When、Where、If … then，子句顺序同上表。
- 用 the 指代系统和对象；全称用 each；缩写写全称。
- shall 后直接接动词：The system shall export…；不写 to be able to、to be capable of、to enable、to allow，也不写 including but not limited to。

## 审查清单

所有类型：

- [ ] 文档只写了一个实体的需求，没有混入成本、进度、开发方法、验收规程。
- [ ] "必需章节"里对应类型列出的每个条目都有内容，或写明了不适用的原因。
- [ ] 修订记录通过了 `blocks/revision.md` 的审查清单，列出了涉及的需求编号；草稿的批准人写"未批准"。
- [ ] 每条需求都有唯一编号；同一需求只写在一处，其他位置用编号引用，或附了交叉索引表。
- [ ] 每条需求的子句顺序是"状态条件 → 触发事件 → 系统名 → 应 → 系统响应"，触发事件不超过一个。
- [ ] 用通用句式的需求都不带适用条件。
- [ ] 每条需求只有一个系统响应。
- [ ] 每条需求的系统名是一个系统或部件的名称。
- [ ] 全文情态词只有"应""不得""可以""宜"；需求句只用"应"，目标用"宜"并单独成节或标为目标。
- [ ] 需求句里"应"后面没有"能够""具备……的能力""可以"。
- [ ] 需求句里没有"以便""为了"引出的目的说明，也没有括号补充。
- [ ] 每条事件驱动需求都检查过无效输入、超时、失效：有对应的"若……则……"需求，或在工作记录里写了不需要的原因。
- [ ] 每个量都有数值、单位和范围或容差。
- [ ] 需求句里没有不可测量的形容词和副词，也没有逃逸条款和绝对词；"让需求可验证"一节的词表用作判定示例，不是穷举。
- [ ] 每条需求指向本条以外的内容时写出了名词，没有用"它""该""此""上述"。
- [ ] 需求里没有设计方案；每条设计约束的理由属性写了约束来源。
- [ ] 每条质量属性需求都有可验证的指标。
- [ ] 每条需求附带了本类型要求的属性集（SyRS、SRS 16 项，其他类型 5 项），拿不到的值写"未定"。
- [ ] 追溯逐条通过了 `blocks/traceability.md` 的审查清单。
- [ ] 每个图、伪码或状态机旁边都有自然语言描述。
- [ ] 正文的待定项都写成 `【待补：TBD-n】`，每个编号在待定项清单里写了缺什么、原因、由谁确定、措施、关闭日期。
- [ ] 审模式下，需求验证和需求确认分开报告，确认部分留了 `【待补】`；报告了与上层文档的一致性和三类内部矛盾的检查结果。
- [ ] 英文需求用 shall，全称用 each，EARS 关键词按原文写。

仅 SRS：

- [ ] 引言写明了预期读者，范围写明了做什么和不做什么。
- [ ] 总体描述里没有具体需求。
- [ ] 每个外部接口都写了名称、目的、输入来源或输出去向、有效范围和精度、单位、定时、格式。
- [ ] 具体需求一章在章首写明了组织方式。
- [ ] 附录写明了是否属于需求。

仅 PRD：

- [ ] "背景与目标"里每个目标都有指标和目标值。
- [ ] 需求一章在章首写明了分组方式。

## 示例

改写前（PRD 里的一节）：

```markdown
### 登录
- 系统应快速响应用户的登录请求，并在必要时锁定账户。
- 用户可以用手机号/邮箱等方式登录（提升转化率）。
```

改写后（PRD 带 5 项属性；原稿没给的数字和条件都留作待定项）：

```markdown
| 编号 | 需求 | 理由 | 上级或来源追溯 | 优先级 | 验证方法 |
| --- | --- | --- | --- | --- | --- |
| REQ-AUTH-001 | 当用户提交手机号和密码时，认证服务应返回登录结果。 | 提升转化率 | 原稿"登录" | 未定 | 测试 |
```
