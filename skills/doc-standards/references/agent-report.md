# Agent 给用户的结果汇报

## 适用

- 读者：等 Agent 交付的用户。用户读汇报时常常同时在做别的事，可能不记得上下文，也可能用机器翻译读。
- 用在：任务做完后的结果汇报、做到一半的进度说明、问题排查结论、请用户做决定或确认、多张任务卡、issue 或变更的汇总。
- 不适用：
  - 用户、系统或调用方指定了输出格式（如只要 JSON）：只输出指定格式，不加模板和说明文字。
  - Agent 写进项目的文件：按文件类型找类型文件，如 `readme.md`、`design.md`、`test-docs.md`。
  - 写进仓库的故障复盘、排查记录 → `base.md`（本 skill 尚未收录，告诉用户；与 `lifecycle-other.md` 的说明一致）
  - 正式提交的测试报告 → `test-docs.md`；正式科技报告 → `tech-report.md`。
  - PR 描述：本 skill 未收录，按项目的 PR 模板写。
  - 代码、代码注释、commit message 不在本 skill 范围。

## 必需章节

先判断这次回复属于哪一类，按对应骨架写。一次回复同时含多类内容时，可以合并骨架，例如结果汇报里加入排查结论的"原因""证据"节。没有内容的节整节删掉。普通的解释或建议不套模板。

### 结果汇报

1. **首句**：`<状态词>：<完成范围与结果>。` 完成范围写到读者能判断"做了哪部分"，如"已完成：登录刷新逻辑的代码修改。iOS 端未验证。"
2. **改动**：一条改动一行，写 `路径` 和改了什么。超出任务范围的改动各占一行，排在范围内改动之后，行末写"这项超出本次任务范围"，再在"待确认"里请用户选撤回或保留。
3. **验证**：一项检查一行，格式 `<状态词>：<检查方法与覆盖范围> — <结果 / 原因 / 关键失败输出 / 确认方法>`。没执行或失败的检查写在这里，不写进"未做"。
4. **未做**（可选：任务范围内有没做的事时）：`<没做的事> — <原因>`。
5. **待确认**（可选：有要用户决定或补充的事时）：一条写一个事项；事项有多个选项时，在事项下按"请求决定"列编号选项。"验证"里写过的缺失条件，只在要用户动手或提供条件时列进来，并且只写要用户做什么。

### 进度说明

1. **首句**：`进行中：<动作><对象>。` 通常只有这一句。动作失败或被阻塞时，状态词换成"失败"或"阻塞"。

### 排查结论

1. **首句**：写原因；原因没查实时写"原因未确认"。
2. **现象**：用户看到的行为和报错。
3. **原因**：查实的原因，或写"未确认"加确认方法。
4. **证据**：每条一项，格式见"验证与证据"。
5. **验证**（可选：做过或该做复现、修复检查时）：格式同结果汇报。
6. **建议**：一个动作。

### 请求决定

1. **首句**：写要用户决定的事。
2. **编号选项**（首句后直接列，不加节名）：每项 `<动作> — <后果>`；推荐项放第一，动作后标"（推荐）"。

### 多项总结

1. **首句**：写总体结论，或写总结范围，如"本总结包含移动端登录模块的 3 项需求。"
2. **术语**（可选：有专用词时）：各项共用的定义，只在这里写一次。
3. **共同条件**（可选：多项共享前提时）：只写一次，各项不再重复。
4. **分组**（不加"分组"节名，直接用 `<组号>. <组名>` 作标题）：每项写加粗的原标题和元数据（如规模、优先级、类型），再写"问题"和"要做"。
5. **待确认**（可选：来源缺少事实时）：每条 `未确认：<来源缺少的事实> — <确认方法>`。

## 写作规则

### 与 base.md 的差异

下面几处按本文件写，base 清单的对应条目按这里判定：

- 缺的事实：写进"待确认"，一句一条，不用 `【待补：缺什么】` 占位，因为用户读汇报，不填汇报。例如需求卡没写重试次数，就把"重试几次"列进"待确认"。base 清单的"【待补】"一条标不适用，改查本文件清单的"缺的事实"一条。
- 交付说明：回复本身就是交付物，没有交付说明。base 要求写进交付说明的内容不写，base 清单的交付说明一条标不适用。
- 自查标记：写和改写模式下，两份清单的逐条标记不写进回复；审模式下，逐条结果就是交付物。
- 加粗：加粗的节名是固定标题，不算强调，不受 base"加粗只给漏看会出错的内容"限制。
- 引导句：节名下的列表直接列，不写引导句。
- 两层列表："待确认"事项下的编号选项是第二层列表，是 base"列表只用一层"的例外。

### 状态词

- 状态只用下表 10 个词。

| 状态词 | 什么时候用 | 同时必须写出 | 不用这些说法 |
| --- | --- | --- | --- |
| 已完成 | 所述完成范围的动作全部做完，没有已知结果否定它 | 完成范围 | 搞定、OK、done、基本完成 |
| 部分完成 | 完成范围里有没做或做失败的部分 | 没做和失败的部分 | 大致完成 |
| 未开始 | 还没动手 | 完成范围 | 待办、TODO |
| 进行中 | 动作已开始，没有结束 | 动作和对象 | 处理中、跟进中 |
| 已验证 | 检查执行了且通过 | 检查方法、结果、覆盖范围 | 已测试、应该没问题 |
| 未验证 | 已知没执行这项检查 | 原因 | 理论上可行、应该可以 |
| 失败 | 动作或检查执行了，结果不符合要求 | 关键失败输出原文 | 有点问题、不太行 |
| 跳过 | 有意不执行 | 原因 | 略过、忽略 |
| 阻塞 | 缺少条件，无法继续 | 缺什么条件 | 卡住、受阻 |
| 未确认 | 是否执行或结果如何缺少证据 | 确认方法（命令、文件或要问的人） | 可能、大概、应该是 |

- 首句的主状态和"验证"里的每一项写成"状态词：对象"；首句里补充的第二个状态可以写成"<对象><状态词>"，如"iOS 端未验证"。不用"已"加普通动词代替状态词：写"已完成：登录刷新逻辑的代码修改"，不写"已修改登录刷新逻辑"。
- 工作状态和验证状态分开写。"已完成"只说动作做完，不代表已验证；代码改完但没跑检查时写"已完成：代码修改。运行效果未验证。"
- 判断整项任务能不能写"已完成"时，先列出验收条件：用户的要求、项目里适用的要求（如必须通过的测试）、任务目标。任一必需检查没执行或失败，整项写"部分完成"，并列出缺的部分。
- 检查执行了但没通过时，这项检查在"验证"里写"失败"，整项状态按上一条写，不用"已完成，未验证"盖过失败。
- "验证"里只用已验证、未验证、失败、未确认。已知没执行的检查写"未验证"，原因写明缺什么条件或为什么不跑，如"未验证：集成测试 — 本机没有 Redis"，这时首句写"Redis 下的限流行为未验证"。不知道是否执行过、结果如何时，才写"未确认"。
- 汇总需求、任务卡时只复述需求，不给需求加工作状态或验证状态；汇总实际成果时照常写状态。

### 验证与证据

- 关于修复效果、运行行为、检查结果的结论，都写一项验证，结果汇报和排查结论写在"验证"节，例如"已验证：`npm test -- auth`，只跑 Android 模拟器 — 42 个用例通过"。
- 读文档、读代码只能支持"资料里写了什么"的结论，写明依据的资料；只有实际运行过检查，才写"已验证"。
- 检查失败时，从工具输出里原样摘出关键的失败行，不转述：单行用反引号写在"—"后面；多行另起代码块，缩进放在这一项下面。
- 同一次检查支撑多个结论时，证据只列一次，各结论指向它。
- 证据写成用户能直接打开或重跑的形式：代码写 `路径:行号`，提交写提交号，命令写完整命令；"证据"节每条写 `<位置> — <这条说明了什么>`。

### 不确定

- "可能""大概""应该是"这类词改成两种写法之一：有证据就写结论和证据；没证据就写"未确认"和确认方法。

### 范围

- 只汇报用户要求的任务范围内的事。
- 汇报到最后一个有内容的节结束；影响验收的后续事项写进"待确认"。

### 选项

- 用户没要求的方案不列为选项。
- 后果取决于没查实的条件时，写成"<条件>时，<结果>"，并把条件列进"待确认"。

### 多项总结

- "问题"写现状，不写对原因的猜测。
- "要做"写能检查的结果，不写实现手段，除非来源规定了手段：写"登录失败 3 次后显示验证码"，不写"加一个计数器"。
- 没有可检查结果的描述（如"体验较差"）删掉，或改写成可检查的现象；改写不了就列进"待确认"。
- 任务卡、issue 的原标题保留原文语言。

### 节名和格式

- 节名只用这些固定词：术语、共同条件、问题、要做、改动、验证、未做、待确认、现象、原因、证据、建议。"改动"不写成"变更内容""diff"；"验证"不写成"测试情况""自测"；"待确认"不写成"风险""TBD""遗留问题"。推荐项标"（推荐）"，不写"建议选择""首选"。
- 结果汇报、排查结论的节名用加粗：节下是列表时，加粗节名单独一行，如 `**改动**`；节下只有一句时，写成 `**原因**：<一句>`。
- 多项总结的"术语""共同条件""待确认"和各组组名用同一级标题（二级或三级都可以），原标题用加粗行。

## 审查清单

- [ ] 用户、系统或调用方指定了输出格式时，回复只有指定格式的内容。
- [ ] 首句符合回复类型：结果汇报是"状态词：完成范围"；进度说明是"进行中""失败"或"阻塞"加动作和对象；排查结论是原因或"原因未确认"；请求决定是待决事项；多项总结是总体结论或总结范围。
- [ ] 结果汇报有"验证"节；Agent 改了文件或配置时有"改动"节。
- [ ] 排查结论有"现象""原因""证据""建议"四节。
- [ ] 请求决定在首句后有编号选项。
- [ ] 所有状态都用 10 个状态词之一；首句主状态和"验证"每一项写成"状态词：对象"。
- [ ] 没有"搞定""OK""done""基本完成""已测试""应该没问题""跑过了"。
- [ ] 没有用"已修改""已添加"这类"已+动词"代替状态词。
- [ ] 结果汇报里每个"已完成"所述的对象，在"验证"里都有一项。
- [ ] 有必需检查没执行或失败时，整项状态是"部分完成"。必需检查按用户原始要求和项目的 CI 或测试脚本判定；审模式下拿不到这些材料时标不适用，原因写缺什么材料。
- [ ] 每个关于修复效果、运行行为、检查结果的说法，不管用什么词，都写成了状态词，并带检查方法、结果和覆盖范围。
- [ ] "验证"里只出现已验证、未验证、失败、未确认。
- [ ] 每个"未验证""跳过"写了原因，每个"阻塞"写了缺的条件，每个"未确认"写了确认方法。
- [ ] 每个"失败"都附有原样摘出的失败输出：单行在"—"后用反引号，多行用代码块。
- [ ] 每个"已验证"的检查方法是实际运行的命令或操作，不是读代码、读文档。
- [ ] "证据"和"验证"里的代码引用都写成 `路径:行号`，命令都是可直接重跑的完整命令。
- [ ] 同一条命令的输出在回复里只出现一次。
- [ ] 除原样引用的输出外，没有"可能""大概""应该是"。
- [ ] 每个数字、次数、期限都能在用户输入、文件或工具输出里找到。
- [ ] 缺的事实都在"待确认"里，回复里没有 `【待补】`。
- [ ] 范围外的改动在"改动"里各占一行，排在范围内改动之后，标明超出任务范围；"待确认"里有撤回或保留的选项。
- [ ] "待确认"之后没有其他提议。
- [ ] 选项是编号列表，每项一个动作加后果，推荐项在第一位且标了"（推荐）"。
- [ ] 多项总结的"要做"都是可检查的结果；写了实现手段的，来源里规定了这个手段。
- [ ] 多项总结的"问题""要做"里没有状态词。
- [ ] 任务卡和 issue 的标题与原文一致。
- [ ] 节名都在固定节名表里。
- [ ] 结果汇报、排查结论的节名用加粗；多项总结的节名和组名用同一级标题。
- [ ] 没有空节。
- [ ] 写和改写模式下，回复里没有自查清单的标记结果。

## 示例

Agent 掌握的事实：用户只要求把请求超时改为 30 s；Agent 改了 `src/config.ts`；对话里没有测试运行记录；项目的测试命令是 `npm test -- config`。

改写前：

```markdown
我先看了一下 config.ts，然后把超时改成了 30 秒。测试应该没问题，大概是好了。要不要我再加个重试机制？
```

改写后：

```markdown
已完成：请求超时改为 30 s 的代码修改。运行效果未确认。

**改动**
- `src/config.ts`：请求超时改为 30 s。

**验证**
- 未确认：`npm test -- config` 是否通过 — 运行该命令确认。
```
