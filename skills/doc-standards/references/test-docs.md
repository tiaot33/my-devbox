# 测试计划、测试用例说明、测试报告

## 适用

- 读者：测试人员、测试经理、开发人员、项目经理，以及质量保证人员、审核人员、客户。按合同交付时，需方读 STP、STD、STR 来评估合格性测试是否充分。
- 用在：瀑布、迭代、敏捷、DevOps 项目和维护等非项目活动中的测试计划、测试状态报告、测试模型规格、测试用例说明、测试规程说明、测试日志、测试事件报告（缺陷报告）、测试完成报告。
- 不适用：
  - 被测需求本身的规格 → `requirements.md`
  - 被测模块、接口的设计说明 → `design.md`
  - 测试方针、组织测试实践（29119-3 第 6 章，本文件未收录）→ `lifecycle-other.md`，按其中的策略或规程类写
  - 生产环境故障、线上事故的报告或复盘 → `lifecycle-other.md`，按其中的报告类写
  - README 里的测试命令 → `readme.md`；单独成文的测试环境搭建、运行测试指南 → `tutorial.md`
  - Agent 跑完测试后在对话里给用户的结果汇报 → `agent-report.md`

## 必需章节

### 测试计划

1. **测试背景**：测试项及其版本，引用需求、设计、用户文档；要测试的特征；不测试的特征和特征组合，各写理由。多级计划中，下级计划引用上级的总测试计划。
2. **假设与约束**：包括测试项何时可用、资源可用性、截止期限。
3. **干系人**与**测试沟通**：列出要用测试结果做决定的人和各自要的信息；写明用什么渠道、多久通报一次进度和事件。
4. **风险登记册**：每个风险配一条应急措施，并标出计划依赖的高风险假设。
5. **测试策略**（shall）：测试类型、测试交付项、测试设计技术、进入和退出准则、测试完成准则、独立程度、要收集的度量、测试数据需求、测试环境需求、再测试、回归测试、暂停和恢复准则，共十二项。偏离组织测试实践时写明偏离项（should）。
6. **测试活动与估算**（shall）：任务、任务间依赖、所需特殊技能、每项任务的工作量。
7. **人员配备**（shall）：角色和职责，包括提供测试项和测试环境的小组。招聘和培训需求（should）。
8. **进度**（shall）：测试里程碑、测试项交付时间、每种资源（设施、工具、人员）的使用时段。
9. **需求追溯**（可选：按 8567 写时必需）：测试到需求、需求到测试双向追溯，写法见 `blocks/traceability.md`。
10. **批准**：写批准人姓名和职务，留签名和日期位置；团队在工具里审批时，可以引用审批记录（PR、Jira 的批准链接）代替签名。

### 测试状态报告（可选：完全符合时必需；剪裁时按是否需要阶段汇报定）

1. **报告期**与**测试状态**。
2. **相对计划的进度**、**阻碍进度的因素**、**测试度量**、**新增和变化的风险**、**下期计划的测试**。

### 测试模型规格（可选：完全符合时必需；剪裁掉时写理由）

1. **唯一标识**、**目标**、**优先级**、**测试策略摘录**（shall）。
2. **测试模型**（shall）：推导用例所用的模型，如等价类划分、状态转换图、判定表、分类树，以及要求的覆盖。
3. **追溯**（shall）：模型对应的需求或测试依据。

### 测试用例说明

1. **测试覆盖项**（shall）：每项有唯一标识、描述、优先级、追溯。
2. **测试用例**（shall）：每个用例有唯一标识、目标、优先级、追溯、前置条件、输入、预期结果。
3. **环境要求**：硬件、软件、特殊设施或经过专门训练的人员。
4. **用例间依赖**（可选：有必须先执行的用例时）：列出前序用例并说明依赖性质。
5. **评价准则**（可选：结果需要额外判定规则时）：允许的持续时间和故障次数、结果不明确时重测的条件。

### 测试规程说明

1. **唯一标识**、**目标**（引用所执行的每个用例）、**优先级**（shall）。
2. **启动**（shall）：执行前的准备和启动动作。
3. **有序的测试用例**（shall）：按执行顺序列出用例，每一步单独编号，写操作动作、预期结果和评价准则。
4. **与其他规程的关系**（shall）。
5. **停止与收尾**（shall）：暂停、重启点、停止、恢复环境，以及出现异常时怎么处理。

### 测试数据需求与测试环境需求（可选：完全符合时必需；剪裁掉时写理由）

1. **测试数据需求**（shall）：标识、描述、责任方、需要的时段、重置需求、用完后的归档或处置。
2. **测试环境需求**（shall）：标识、测试环境项、描述、责任方、需要的时段。
3. **测试数据就绪报告**、**测试环境就绪报告**（shall）：各写唯一标识和就绪状态。

### 测试日志

1. **日志描述**：适用于全部条目的信息，即测试项及版本（构建号）、测试环境。
2. **条目**（shall）：每条有唯一标识、日期时间、描述、影响。开始和结束各记一条。
3. **实际结果和测试结果**（shall）：每个用例的实际结果，以及与预期结果比较得出的通过或失败。

### 测试事件报告

1. **时间信息**、**报告人**、**上下文**（shall）：上下文写测试项及版本（构建号）、测试环境、所执行的规程和用例。
2. **事件描述**（shall）：输入、预期结果、实际结果、异常现象、日期时间、所在规程步骤、环境、是否尝试重复执行、测试者、观察者。没有规程时，写从初始状态起逐步编号的复现步骤，并写尝试复现几次、复现成功几次。
3. **报告人对严重程度的评估**、**报告人对优先级的评估**（shall）：分两项写，刻度用测试计划定义的等级。
4. **风险**（shall）：事件对测试计划、测试设计、用例、规程的影响。
5. **事件状态**（shall）。

### 测试完成报告

1. **已执行测试的摘要**（shall）：先用一段写结论：测试项是否满足完成准则、是否建议发布、由谁接受残余风险。再写测试了哪些项及版本（构建号）、在什么环境、引用了哪些计划、规程、日志、事件报告。
2. **与计划的偏离**（shall）：每项偏离都写原因。
3. **测试完成评估**（shall）：逐条对照计划里的完成准则写满足或未满足；列出没有充分测试的特征或组合并写理由。
4. **阻碍进度的因素**、**测试度量**（shall）。
5. **残余风险**（shall）：列出所有未解决的事件，写明谁接受了这些风险。
6. **测试交付项**（shall）、**可复用的测试资产**（should）、**经验教训**（shall）。
7. **评价**：每个测试项的结论写"通过""有条件通过""不通过"之一，有条件时列出条件和限制；依据是测试结果和计划中的通过准则。
8. **批准**：写法同测试计划第 10 项。
9. **环境差异与改进建议**（可选：按 8567 写 STR 时必需）：测试环境与实际运行环境的差异及对结果的影响；改进建议，没有就写"无"。

## 写作规则

### 先定文档组合

- 先问清或从上下文判断两件事：组织声明对 29119-3 完全符合还是剪裁符合（4.1.1）；是否按 GB/T 8567 的合同交付格式写（出现"合格性测试""需方""CSCI"时按 8567）。用户没提 29119-3 时，按剪裁符合写。
- 符合性声明和剪裁理由写进文档：放在信息块的"引言"里，或单列一行"剪裁说明"。剪裁理由可以逐项写、按组合写一句，或引用别处的说明。判断过程写进交付说明。
- 文档量按风险定：低风险或敏捷团队可以写一页的发布测试计划、只为高风险特性写用例、发布结束写一页的总结报告；安全相关系统按完全符合写全套。
- 一页的发布测试计划至少写测试背景（测什么、不测什么）、风险与应急措施、策略中的测试类型、进入和退出准则、测试环境、回归测试、人员与进度、批准；其余 shall 项在剪裁说明里用一句话统一给理由，例如"敏捷发布计划，未列项在站会同步"。
- 一页的完成报告至少写完成准则是否满足、残余风险由谁接受，例如"高风险故事全部完成，剩余风险由产品负责人接受"。
- 文档可以是测试管理工具记录、电子表格，可以拆分或合并；标题可以改名、合并、增补。
- 项目已用测试管理工具或表格时，按其中的字段交付。
- 按 8567 写时只出三份：STP；STD（设计、用例、过程合一）；STR（结果、记录、总结合一）。8567 允许大项目把测试计划拆成计划、设计说明、规程、用例几卷。

### 计划

- 把测试充分性写成可以度量的门槛，例如"每条语句至少执行一次""需求覆盖率 100%"，并写出用什么方法判断是否达到。
- 暂停准则旁边写恢复测试时必须重做哪些活动。
- 进入准则写到每个测试级别，例如"用例已设计、已追溯到需求、已经干系人签批"。
- 进入和退出准则写每个测试级别或活动何时开始、何时结束；测试完成准则写整个测试何时算做完，常和设计技术要求的覆盖一起写。两者相同时可以合写，注明"退出准则即完成准则"。
- 完成准则或度量用到严重程度、优先级时，在计划里写出等级定义，或引用缺陷工具里的定义；项目没有定义时写 `【待补：严重程度等级定义】`。
- 测试策略、进入和退出准则、环境需求用"项 / 内容"两列表格写，单元格里的短语并列用顿号，不写成两层列表。
- 计划和报告用角色名或人名写执行者，例如"王敏执行""开发组修复"；规程步骤用祈使句。计划和报告的读者有多类，这条代替 base 的"用'你'称呼读者"。

### 用例与规程

- 预期结果写可观察、可比对的具体输出，例如界面状态、返回码、字段值；数值写精确值，允许偏差时在预期结果里写容差或阈值，例如"响应时间 ≤ 200 ms"。
- 输入逐项写值或数据集名称，输入之间有时序等关系时写出来。
- 选输入时覆盖额定值、最大值、最小值；用有效数据测过载等最坏情况，用无效数据测非常规输入。
- 用例按"不看设计文档也能执行"来写，因为一个用例会被多个设计和小组长期引用。
- 选用例的理由和分析写进测试模型规格；未写测试模型规格时，写进测试用例说明的"目标"字段。规程只写要执行的步骤，编号步骤按 `blocks/steps.md` 写，命令按 `blocks/code-sample.md` 写。
- 一个规程覆盖多个需求时，在每一步旁标出它对应的需求编号。
- 用例和规程按所覆盖需求的风险排优先级，规程的风险取其中最高的用例。
- 按 8567 写 STD 时，安全和保密提示用"警告"或"注意"开头：可能伤人或丢数据的用"警告"，可能损坏设备或测试环境的用"注意"。位置和句式按 base 的警告规则。

### 执行记录与事件报告

- 实际结果只抄录执行时的输出，例如日志、截图、命令输出，并标出对应的日志条目标识；没有执行数据时写 `【待补：用例 X 的实际结果】`。
- 每条日志条目写出由它产生的事件报告标识；每份事件报告写出对应的日志条目标识和规程步骤。
- 事件报告标题写观察到的现象，例如"提交订单后返回 500"；原因确认后再写归属模块。实际结果与预期不符，可能来自环境、数据或用例本身。
- 事件描述写入有助于定位原因的观察，例如同一时段其他用例的执行情况、执行时与规程的偏差。

### 报告

- 状态报告和完成报告用测试计划里定义的度量，名称和口径不变。
- 用表格列出每个用例的完成状态，例如"符合预期""遇到问题""与规程有偏差"；不是"符合预期"的用例，引用后文详细条目。
- 遇到问题的用例写出：出问题的步骤、相关事件报告、重试次数和每次结果、从哪一步恢复。
- 偏离规程的用例写出：偏离内容、理由、对用例有效性的影响。

### 引用与自成体系

- 一项内容已在别的文档里时，可以只写引用，引用写明文档标识和版本，并把被引文档附上或保证读者能拿到。
- 按 8567 交付需方的 STP、STD、STR 各自成体系，评估需要的内容写在本文档里；同一文档内部的重复可以用引用。

## 审查清单

通用：

- [ ] 文档的引言或剪裁说明写明了完全符合还是剪裁符合；剪裁掉的 shall 项有逐项或按组合给出的理由
- [ ] 计划、规格说明、完成报告的信息块都有唯一标识、状态、变更历史
- [ ] "必需章节"表里的文档名首次出现时括注了 29119-3 英文名；项目自有叫法的除外
- [ ] 计划和报告用角色名或人名写执行者，没有用"你"

计划：

- [ ] 写了不测试的特征，每项都有理由
- [ ] 测试策略包含必需章节第 5 项列出的十二项，或在剪裁说明里给了理由
- [ ] 测试充分性和完成准则都是可以判定达到与否的量
- [ ] 准则里用到的严重程度、优先级，在计划里有等级定义或引用了工具里的定义
- [ ] 暂停准则旁写了恢复时要重做的活动
- [ ] 每个风险都有应急措施
- [ ] 下级计划引用了上级计划

用例与规程：

- [ ] 每个用例都有标识、目标、优先级、追溯、前置条件、输入、预期结果
- [ ] 没有只写"正常""成功""快"这类形容词的预期结果；数值类预期结果都有精确值、容差或阈值
- [ ] 追溯逐条通过了 `blocks/traceability.md` 的审查清单；每个用例和规程追溯到的上游是需求或用户故事
- [ ] 规程的每一步都单独编号，并有该步的预期结果
- [ ] 规程写了启动、停止和收尾

执行记录与事件报告：

- [ ] 测试日志、事件报告、完成报告都写了测试项版本或构建号
- [ ] 测试日志的开始和结束各有一条带日期时间的条目
- [ ] 每个实际结果都能对上日志条目标识或执行时间；对不上的写成了 `【待补】`
- [ ] 每份事件报告都有输入、预期结果、实际结果、环境名称和版本，以及所在规程步骤或编号的复现步骤
- [ ] 严重程度和优先级分两项写，刻度与计划中的定义一致
- [ ] 每份事件报告都有当前状态
- [ ] 事件报告标题写的是现象，不是未经确认的原因

状态报告与完成报告：

- [ ] 测试状态报告写了报告期和相对计划的进度
- [ ] 完成报告第一段写了是否满足完成准则、是否建议发布、由谁接受残余风险
