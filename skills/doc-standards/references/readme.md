# README

## 适用

- 读者：分三类，需求逐级叠加：开发者也需要使用者的信息，贡献者也需要开发者的信息。
  - 使用者：想把代码装好跑起来。
  - 开发者：想从源码构建并运行测试。
  - 贡献者：想提交改动。
- 读者背景：有编程基础，第一次接触本项目。PR、CI、CLI、API、URL 对这类读者不用展开；DCO、SPDX 这类合规缩写首次出现时写全称或加链接。
- 用在：代码仓库根目录的 README、monorepo 中各代码包顶层目录的 README、代码改动后同步 README。
- 不适用：
  - 完整的分步教程、快速入门 → `tutorial.md`
  - 导出函数、命令参数、接口的完整说明（README 里放链接）→ `api-reference.md`
  - 面向最终用户的产品使用说明、安全须知 → `user-manual.md`
  - CONTRIBUTING、行为准则等单独成文的仓库规范文件 → `lifecycle-other.md`
  - 版本发布公告、弃用通知 → `public-notice.md`
  - CHANGELOG → `base.md`
  - GitHub 个人主页 README（与用户名同名的仓库）→ `base.md`

## 必需章节

按下列顺序排。标为"无标题"的部分直接写正文，不加二级标题。README 用中文写时，章节标题用中文。下列章节名是 `base.md` 标题规则所说的"类型文件规定的固定标题"，照写，不改成陈述句或问题。

1. **标题**：一级标题，与仓库名、目录名、包管理器里的包名一致。用别的名字作标题时，在后面用斜体括号写包名，如 `# 标准 README 风格 _(standard-readme)_`，并在长描述里说明为什么不一致。
2. **徽章**（可选：项目有 CI、包版本、覆盖率等状态可展示时）：无标题，紧跟标题，每个徽章单独一行。
3. **简短描述**：无标题，单独一行，说清项目做什么。
4. **长描述**（可选：需要说明项目为什么有用、与同类项目有何不同、依赖哪些外部应用、只支持哪些平台时；项目处于弃用、停止维护、未正式发布或不接受贡献的状态时必需）：无标题。有上述状态时，第一句写明状态，必要时指向替代项目。细节放到后面的章节，动机和来源写长了就移到"背景"一节。
5. **目录**（可选：README 达到 100 行时加）：从下一节开始列，不含标题和目录本身，至少覆盖全部二级标题，每项是页内锚点链接。
6. **安全**（可选：项目处理密钥、权限或外部输入，或有漏洞报告渠道时）：写安全相关的配置要求和报告漏洞的渠道。安全问题不重要时，这些内容放进第 10 项附加章节。
7. **背景**（可选：需要交代动机、依赖的思想或来源时）：写项目为什么存在、借用了哪些思想或上游项目。
8. **安装**（可选：仓库有可运行代码时加；只有文档的仓库省略）：
   - 先列前置条件：语言或运行时的最低版本，或支持的操作系统和架构，各附官方下载链接。
   - 给出安装代码块：发布到包管理器的写包管理器命令（如 `npm install PACKAGE_NAME`），否则链接到发布页：地址指向 `releases/latest`，链接文字写"发布页"。
   - 安装步骤按新手能照做的粒度逐步列出。
   - 有需要手动安装或不常见的依赖时，加 `依赖` 子节。
9. **用法**（可选：同"安装"）：
   - 先给最常见、最简单的用法，再给复杂用法。
   - 库：给导入语句和最小可运行示例。
   - 示例有标准输出时给出预期输出；没有时写明运行后得到什么结果，如生成哪个文件。
   - 有命令行工具时加 `命令行` 子节。要给语法格式时，单独放进一个 `text` 代码块，前面写"语法："，后面另给一条能直接运行的示例命令。
   - 长示例放进仓库里可运行的示例文件并链接。
10. **附加章节**（可选：如"配置""常见问题""支持""路线图"）：放在"用法"和"API"之间，各用自己的标题，不写成"附加章节"。上面四个名称算本类型的固定标题；其余新加的章节标题按 `base.md` 写成陈述句或问题。
11. **API**（可选：项目导出函数、类或事件时）：写导出对象的签名、返回类型、回调、事件和容易用错的地方；用文档生成器时只放一句话和指向 `API.md` 或参考站点的链接。
12. **维护者**（可选：有固定维护人时）：只列负责方向和日常维护的人，每人至少一种联系方式。
13. **致谢**（可选：要感谢资助方、上游项目或重要贡献者时）：标题用"致谢"。
14. **如何贡献**：
    - 写明在哪里提问、报 bug、提需求，给出 issue 页、讨论区或邮箱链接。
    - 写明是否接受 PR，以及贡献要求，如签署 DCO、代码规范、测试要求。
    - 接受代码贡献时，给出从全新克隆开始的构建命令和运行测试的命令，并说明需要的构建工具、环境变量和外部服务。步骤较长时放进 CONTRIBUTING.md。
    - 链接 CONTRIBUTING.md 和 CODE_OF_CONDUCT.md（存在时）。先在根目录、`docs/`、`.github/` 下找这两个文件。
15. **许可证**：放在最后一节。写 SPDX 许可证标识符或全称、版权持有人，并用相对链接指向仓库里的 LICENSE 文件全文，如"本项目以 [MIT](LICENSE) 许可证发布，版权归 <持有人> 所有。"内部或私有仓库没有开源许可证时，写"仅限 <组织> 内部使用，未开源（`UNLICENSED`）"，不放 LICENSE 链接。

## 写作规则

### 文件与位置

- 文件名用全大写的 `README.md`，放在仓库根目录。仓库已有 `.github/README.md` 时，GitHub 优先显示它，改动要同步到那一份。
- monorepo 中每个代码包的顶层目录各放一份 README，说明这个包是什么、谁维护、怎么用。
- 有多种语言版本时，按 `README.<BCP 47 语言标签>.md` 命名，标签不带地区子标签，中文版用 `README.zh.md`；`README.md` 留给英文版。只有一份中文 README 时直接用 `README.md`。以中文为主、另有英文译本时，改名前先问用户。

### 篇幅与内容边界

- README 只写开始使用和参与贡献所需的信息；架构、完整配置、深入教程放进 docs 目录或 wiki 并链接。为缩短篇幅拆内容时，把内容移走，读者需要的信息不删。
- 文件大小控制在 500 KiB 以内，超出部分 GitHub 不显示。
- 通用技术或流程（如怎么装 Node.js、怎么用 Git）链接到官方文档，不在 README 里重写。

### 简短描述与元数据

- 简短描述用普通段落，不用 `> ` 引用块。英文少于 120 个字符；中文按 `base.md` 描述句上限，不超过 40 字。
- 简短描述与包管理器的 `description` 字段、GitHub 仓库的 About 描述保持同一句话。
- 静态徽章（如许可证类型）用仓库内的本地图片，仓库里还没有这张图片时写 `【待补：徽章图片路径】`；动态徽章用 shields.io 一类服务。每张图片都写替代文字。

### 命令与代码示例

- 命令和代码示例按 `blocks/code-sample.md` 写。
- 实测在全新克隆的仓库里做：写完安装、用法、构建、测试步骤后，按 README 实际执行一遍。

### 链接

- 指向仓库内文件和图片的链接用相对路径，在克隆副本里也能打开；以 `/` 开头的路径相对仓库根目录。链接文字写在一行内。
- 交付前逐个检查链接都能打开、锚点都能跳转。

### 许可证与状态

- 仓库里找不到 LICENSE 文件、用户也没说明时，许可证一节写 `【待补：许可证】`，由用户选定许可证。理由：没有许可证时，他人默认不得复制、分发或修改代码。
- 状态写成可核对的事实，如"自 2026 年 3 月起不再维护，请改用 <替代项目>"。
- 只写已经发布的功能；计划中的功能写进 issue 或路线图文档，README 里链接过去。

### 代码改动后同步 README

同步按 `SKILL.md` 的"改写"模式做：原稿是现有 README，事实来源是本次代码改动的 diff 或 PR 描述。

- 动笔前从 diff 里列出改到的包名、命令名、参数名、配置项名、环境变量名、构建命令，在根目录 README、各子包 README 和示例文件里逐个全文搜索，每处命中都按下表检查。
- 在改代码的同一个提交或 PR 里改 README；评审时检查 README 是否同步。
- 按改动类型对照要改的章节：

  | 代码改动 | 要同步的位置 |
  | --- | --- |
  | 包名、命令名、仓库名变了 | 标题、安装命令、用法示例、徽章链接 |
  | 运行时最低版本、依赖、支持平台变了 | 安装 · 前置条件、依赖子节 |
  | 公开 API、命令行参数、配置项变了 | 用法、API、相关示例文件 |
  | 构建脚本、测试命令、环境变量变了 | 如何贡献中的构建与测试命令 |
  | 项目用途变了 | 简短描述、包管理器 description、GitHub About |
  | 弃用、停更、转交维护 | 长描述第一句、维护者 |
  | 许可证变了 | 许可证一节、LICENSE 文件、徽章 |
  | 文件或标题改名 | 目录、相对链接、锚点 |

- 先删掉已经不成立的内容，再补新内容。
- 按改动后的现状改写，不用"现在支持""新增""最新版""目前"这类时间词；变更历史写进 CHANGELOG 或发布说明。
- 同步后重新执行 README 中受影响的命令和示例，并重查链接。

### 英文 README

- 章节标题用 SR 规定的英文名：Install、Usage、Maintainer 或 Maintainers、Thanks（或 Credits、Acknowledgements）、Contributing、License；其余标题用 sentence case，任务型标题用动词原形开头。
- 输出前写 "The output is similar to the following:"；不写 "run the following command"。

## 审查清单

- [ ] 文件名为 `README.md`，位于仓库根目录或各代码包的顶层目录。
- [ ] 一级标题与仓库名或包名一致；不一致时有斜体括号包名，且长描述说明了原因。
- [ ] 徽章、简短描述、长描述没有加标题。
- [ ] 标题后有一行简短描述，不以 `> ` 开头；英文少于 120 个字符，中文不超过 40 字（按 `base.md` 计数）。
- [ ] 简短描述与包管理器 `description` 字段、GitHub About 描述一致（三者都存在时）。
- [ ] 项目已弃用、停更、未正式发布或不接受贡献时，长描述第一句写明了该状态。
- [ ] README 达到 100 行时有目录，目录覆盖全部二级标题，每项链接都能跳转。
- [ ] 章节顺序符合"必需章节"的编号顺序。
- [ ] 章节标题用规定的中文名（安全、背景、安装、依赖、用法、命令行、API、维护者、致谢、如何贡献、许可证），或是附加章节的固定标题、陈述句、问题。
- [ ] 安装一节列出了运行时最低版本或支持的操作系统和架构，且有安装代码块（文档仓库除外）。
- [ ] 用法一节第一个示例是最简单的常见用法；示例有标准输出时附预期输出，没有时写明运行后得到什么结果。
- [ ] 有命令行工具时，有"命令行"子节。
- [ ] 命令和代码示例逐条通过了 `blocks/code-sample.md` 的审查清单。
- [ ] 安装、用法、构建、测试命令已在全新克隆中实测，或已在交付说明里列为未实测。
- [ ] "如何贡献"写明了提问或报 bug 的渠道，以及是否接受 PR。
- [ ] 接受代码贡献时，有从全新克隆开始的构建命令和测试命令（或指向 CONTRIBUTING.md 的链接）。
- [ ] 根目录、`docs/`、`.github/` 下存在 CONTRIBUTING.md、CODE_OF_CONDUCT.md 时，README 链接了它们。
- [ ] 许可证是最后一节，写了 SPDX 标识符或全称、版权持有人，并用相对链接指向 LICENSE；内部或私有仓库写明"仅限内部使用，未开源"即通过。
- [ ] 指向仓库内文件和图片的链接都是相对路径，所有链接都能打开。
- [ ] 每张图片和徽章都有替代文字。
- [ ] 正文没有"现在支持""新增""最新版""目前"这类时间词，也没有写未发布的功能。
- [ ] 代码改动后同步 README 时：README 的改动与代码改动在同一个提交或 PR 里；拿不到提交上下文时标不适用，并在交付说明里提醒用户。
- [ ] 代码改动后同步 README 时：每个改动名称都在 README 和示例文件里搜索过，命中处已按对照表改好。

## 示例

改写前（代码改动后同步时常见的写法）：

```markdown
## 用法
请运行以下命令：

    foo build [--out dir] ...

现在新增支持输出目录！
```

改写后：

````markdown
## 用法
### 命令行

把 `src/` 构建到指定目录：

```sh
foo build --out OUTPUT_DIR
```

把 `OUTPUT_DIR` 替换为构建产物的存放目录。命令运行后产物写入该目录，终端不输出内容。
````
