# 架构描述

## 适用

- 读者：要从架构里取信息的各方（逐类清单见"写作规则 · 利益相关方与关注点"），拿文档来理解、评估、做决策、维护或交接。
- 用在：系统或软件的架构文档、arc42 文档、C4 图集及配套文字、架构评审材料、方案对比用的多份架构描述。架构图按本文件写，不转 `dataviz`。
- 不适用：
  - 单条架构决策记录（ADR）→ `domain-modeling` skill
  - 模块、接口、数据结构的详细设计 → `design.md`
  - 外部接口的字段、错误码、示例 → `api-reference.md`
  - 需求规格、PRD → `requirements.md`
  - 运维操作步骤、故障处置手册 → `user-manual.md`
  - 项目首页上的简介和用法 → `readme.md`

## 必需章节

两种骨架选一种：用户或团队已经在用 arc42 时，按下文"用 arc42 时"的 12 节写；没有约定时，按下面 10 章写，顺序参照 42010 第 6 章的子条款。一级章节用下列章节名或团队已有的章节名，作固定标题；视图小节标题写成"<视点名>视图：<范围>"，如"部署视图：生产环境"；其余小标题按 `base.md` 写。

1. **标识与概述**：首段不超过 3 句，写系统是什么、整体结构（如"三个服务经消息队列异步协作"）、本份架构描述（architecture description，AD）给谁用、做什么用。首段之后放标识表，列：关注实体的名称和边界、AD 用途、版本和日期、适用的时期或情境、补充信息（项目或组织要求的内容）、架构评估结果（没做过写"无"）。
2. **利益相关方**：一张表，列"角色、代表人或联系人、对本文档的期望"。
3. **关注点**：先写质量目标，再写关注点表。关注点表列编号、关注点、利益相关方、框定它的视点；这张表就是关注点与利益相关方的对照表。
4. **利益相关方视角与方面**（可选：关注点多到需要分组，或要把关注点细化追溯到视图时加）：列出视角和方面，各自对应哪些关注点、由哪些视点覆盖。
5. **视点**：每个视点写名称、框定的关注点、面向的利益相关方、模型种类或记法、来源；可选写本视点不处理的问题（anti-concern）、对应规则、一致性检查方法。引用现成视点（如 C4 的各层图）时，记法和模型种类写出处即可，框定的关注点和面向的利益相关方必须写。
6. **视图**：每个视图标明所依据的视点，由视图组件（图、表、清单、文字）组成。没有其他约定时，至少写上下文视图和构建块视图第 1 层（或 C4 容器图）。系统分布在多台机器或多个容器上时，加部署视图。运行时视图按关注点挑场景。
7. **对应关系与一致性**：列出跨视图、跨模型的对应关系及类型，以及每条对应规则的检查结果。
8. **架构决策与理由**：决策表，或指向 ADR 目录的链接。
9. **风险与技术债**：按优先级列出，每条附降低、缓解或规避的措施；没有已知风险时写"目前无已知风险"。
10. **术语表**：领域和技术术语，含 42010 术语的译名。

## 写作规则

### 框架与符合性声明

- 写到记法、模板或章节顺序时，说明这是团队的选择，不归给 42010。
- agent 只写"参照 ISO/IEC/IEEE 42010:2022 组织"。用户要求声明符合时，告诉用户：必须由持有标准原文的人逐条核对第 6 章，第 6 章的每条要求都必须满足，剪裁过的不算符合。
- 动笔前写明本份 AD 的用途，和系统本身的用途分开写。

### 42010 术语

42010 术语首次出现时必须附英文（比 `base.md` 更严：读者要拿英文去对照标准）。中文译名按下表；国标译名核对后以国标为准。

| 英文 | 本文用词 | 含义 |
| --- | --- | --- |
| architecture description（AD） | 架构描述 | 表达架构的工作产品 |
| entity of interest（EoI） | 关注实体 | AD 描述的对象；2022 版取代 system of interest |
| stakeholder | 利益相关方 | 对关注实体有利益、权利或诉求的角色、个人或组织 |
| concern | 关注点 | 对利益相关方重要的事项 |
| stakeholder perspective | 利益相关方视角 | 看待关注实体的一种思路，与关注点相关；可用来给关注点分组 |
| aspect | 方面 | 关注实体的一个侧面，如功能、结构、信息 |
| viewpoint | 视点 | 为框定关注点而定的一套创建、解读、使用视图的约定 |
| view | 视图 | 构成 AD 一部分的信息单元 |
| view component | 视图组件 | 视图里可单独拿出来的部分，受模型种类或图例约束；取代 2011 版的 architecture model |
| model kind | 模型种类 | 按建模约定区分的模型类别 |
| legend | 图例 | 对视图组件所用约定的非正式说明 |
| correspondence | 对应关系 | 两个或多个 AD 元素之间命名的关系 |
| correspondence rule | 对应规则 | 要求某类对应关系必须成立的约定 |

- 视点一律用"框定"（frame）关注点，相当于提出问题；视图一律用"处理"（address）关注点，相当于回答问题。

### 范围与取舍

- 动笔前问用户各利益相关方要从文档里得到什么。问不到需要或质量需求时，写出推断：需要写进"期望"列，质量需求写成假设，都标 `【待补：与 <角色> 确认】`。
- 按角色给信息：运维要基础设施、部署、外部接口、日志和监控；相邻系统开发者要上下文、外部接口细节和跨接口的端到端场景。
- 第 2 层及以下的分解，只写重要、意外、有风险、复杂或常变的部分，其余省略。
- 功能需求和质量需求链接到需求文档，写明位置，不在 AD 里重抄；链接和版本的写法见 `blocks/citation.md`。

### 利益相关方与关注点

- 利益相关方逐类过一遍：最终用户、运维者、采购方、所有者、供应商、架构师、开发者、建造者、维护者、监管者、认证机构。
- 把与项目成功相悖的一方（政治反对者、潜在攻击者）列为利益相关方，或写明不涉及；列出时写出架构的应对，如谈判方案、预防措施。
- 关注点从需求、目标、约束、假设、依赖、质量属性、已有决策、风险中找，并覆盖全生命周期，不只看开发期。
- 关注点写成视图能回答的问题，如"系统怎么维护？""哪些行为与安全相关？""运行成本是多少？"。
- 每条关注点至少关联一个利益相关方，至少由一个视点框定。
- "期望"列每格写读者要从文档里查到的信息（如"部署拓扑和告警入口"），不写系统要具备的功能或性能。

### 视点与视图

- 视图组件可以是叙述文字、表格、用例模板、职责清单、位置清单，不必都是图或模型。
- 每个视图组件都附图例：图写记号含义，表格写各列含义，叙述文字用一句话写明所用约定（如编号规则、术语出处）。基于模型的组件还写明所用模型种类或建模语言。
- 一个视点可以支配多个视图，如每个子系统一张同类视图。
- 视点和视图可以先视点后视图、两者交替，或视图在正文而视点放附录。选定一种，全文不变。
- 每个视图末尾列"已知问题"：与视点约定的偏差、不一致、未完成项、未决问题。没有就写"无"。
- 对应关系的类型取自 42010 3.11 的示例：等价、组合、细化、一致性、追溯、依赖、约束、满足、义务。例："容器图的 order-api ↔ 部署视图的 Deployment order-api（等价）"。
- 每条对应规则后写"已满足"，或列出不满足它的元素。

### 上下文、结构、运行时、部署

两种骨架里，这几类视图的写法相同；用本文件骨架时，放进"视图"一章，各自标明视点。

- 上下文里列出全部外部通信方和全部外部接口，标出系统边界。
- 业务上下文配一张表：通信方、输入、输出；画数据流，不画依赖。技术上下文写通道和协议，并给出"业务输入输出 → 技术通道"的对照表。
- 构建块视图第 1 层写：整体系统白盒、所含构建块的名称和职责、分解理由。用 C4 时，容器图可以作第 1 层，但必须另写分解理由。
- 用 C4 时，先画系统上下文图和容器图；组件图只在确有价值时画，并考虑自动生成；代码图不进长期文档，交给 IDE 按需生成。
- C4 只管静态结构。业务流程、状态机、领域模型、数据模型用 UML 活动图或状态图、ER 图补充。
- 运行时场景按架构相关性挑，覆盖重要用例、关键外部接口交互、启动和停止、错误和异常。
- 部署视图每个环境都写：生产环境写完整视图，含制品到基础设施的映射和这样部署的理由；开发、测试环境可以只写一张"与生产的差异"表。集群、负载均衡、节点数这类部署细节放部署视图，不放容器图。

### 图

图表的通用写法（表的用途、图的结论、编号、格式）见 `blocks/figure-table.md`。每张图不靠正文也能看懂；图的格式不能显示图例时，在图下方紧跟一张"记号 / 含义"表。具体做法：

- 图标题写出图类型和范围，如"订单系统的系统上下文图"。
- 图例解释形状、颜色、边框、线型、箭头和缩写。UML、ArchiMate、SysML 图也必须有图例。
- 每个元素写明类型（人、软件系统、容器、组件）、名称和一句职责；容器和组件写明技术。
- 每条线单向，标签说清意图并与箭头方向一致，如"发送客户变更事件给"，不写"使用"。容器之间的线写明协议。
- 一张图只用一个抽象层级；职责写具体，不写"业务逻辑"这类泛词。
- 多张图写明阅读顺序。
- 颜色在图内和图间含义一致，黑白打印和色盲读者也能区分。

### 质量目标与质量场景

- 质量目标写在本文件"关注点"一章开头（arc42 为第 1 节），只写最重要的 3～5 个，按优先级排序，每个配一个具体场景；其余放 arc42 第 10 节或关注点表。
- 质量目标写系统的质量属性，不写项目目标（如工期、预算）。
- 质量场景写成可度量的：背景、刺激来源、度量或验收标准。分使用场景（如"峰值时 95% 请求在 1 s 内返回"）和变更场景（如"新增一种支付方式不超过 3 人日"）。

### 架构决策

- 挑关键决策的线索：影响关键或众多利益相关方、实施或改动代价高、对变更敏感、推理不直观、关联架构上重要的需求、带来资本支出。
- 决策的写法见 `blocks/decision.md`。AD 里每条决策写成决策表的一行，列：编号、决策、日期、理由要点、代价与后果、被否决的方案、关联的关注点。需要完整字段（负责人、受影响的 AD 元素、决策标准、约束和假设、备选方案的后果）时，用 `domain-modeling` 写成 ADR，在 AD 里链接。
- 用 arc42 时，解决方案策略一节只写决策要点并链接到决策条目，不重复理由。
- 提到 42010 对决策的要求时，只写"给关键决策写理由"。2011 版要求给关键决策写理由，记录决策本身只是建议；2022 版是否要求记录决策本身待核。

## 示例

改写前（关注点和一条连线）：

```markdown
运维：关注系统稳定性和可维护性。
[订单服务] --使用--> [库存服务]
```

改写后：

```markdown
| 编号 | 关注点 | 利益相关方 | 框定它的视点 |
| --- | --- | --- | --- |
| C-03 | 单个节点宕机时，下单是否中断？中断多久？ | 运维、产品负责人 | 部署视点、运行时视点 |
| C-04 | 升级库存服务时，要不要停订单服务？ | 运维 | 部署视点 |

[订单服务] --预占库存（gRPC，同步）--> [库存服务]
```
