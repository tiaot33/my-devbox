# 设计说明（模块、接口、数据）

## 适用

- 读者：
  - 开发人员：照着实现。
  - 维护人员：照着修改和排障。
  - 其他利益相关方：需方、项目经理、质量保证、配置管理、测试人员，各自要找的信息不同。
- 用在：软件（结构）设计说明（SDD）、接口设计说明（IDD）、数据库（顶层）设计说明（DBDD）、系统/子系统设计说明（SSDD）；项目里叫"概要设计""详细设计"的文档；从已有代码整理出的设计说明。
- 不适用：
  - 需求规格说明、接口需求、数据需求 → `requirements.md`
  - 讲系统由哪些部分组成、为什么这样拆，给评审、运维、相邻团队看的架构描述 → `architecture.md`。讲每部分怎样实现、接口有哪些字段，给实现者看的，用本文件。用户只说"系统设计说明"时按这条分。
  - 给调用方看的接口参数和示例 → `api-reference.md`
  - 测试用例和测试规程 → `test-docs.md`
  - 单条架构决策记录（ADR）→ `domain-modeling` skill

### 先定文档形态

动笔前定四件事，写进工作记录：

1. **用哪套章条。** 没有点名 GB/T 8567 时，按下文"必需章节"的顺序和编号写；它以 8567 7.13 为骨架，补进了 1016 的利益相关方、视点和理由。合同、项目或用户点名 GB/T 8567 时，沿用 8567 7.13 的章、条标题和编号；"必需章节"第 3、4 章的内容写进 1.3 文档概述，模块表放 4.1.1，4.3 引用它。两种情况下，条都可以扩展、细分或缩并，编号随之调整。
2. **拆不拆。** 接口或数据库内容多时，单独写 IDD、DBDD，SDD 里引用；内容少时并入 SDD 对应章。文档名称可以不同于标准。
3. **描述对象。** 写明本文描述的是待实现的设计，还是对已有实现的整理；后者在"基线"里写代码仓库和版本。
4. **粒度。** 系统或子系统级设计写全"必需章节"。只写一个模块或一个功能点时：第 1 章只写要点、标识和基线；第 3、4 章合成一张"关注点 / 回答它的章节 / 记法"表；第 6 章只写模块表、执行概念和接口设计；第 7 章是重点。

## 必需章节

1. **引言**：
   - 要点：放在标识之前，用 2～3 句写用什么方案满足哪项核心需求。
   - 标识：文档标识号、标题、版本号、发布日期与状态、发布组织、作者。同一版本分批分发时加发行号，没有就省略。
   - 系统概述：用途、开发与运行历史、需方、用户、开发方、运行现场。
   - 文档概述：用途、内容、保密要求。
   - 基线：本文依据的设计基线的版本。
2. **引用文件**：每份文件写编号、标题、修订版本、日期；不能从正常渠道获得的，写明来源。
3. **利益相关方与设计关注点**：列出读者角色、每类读者要从本文得到的信息，以及设计关注点。每个关注点给编号，如 C-03"重启后订单状态不丢失"，供视点表和追踪表引用。这一章写进正文，与 base 不同：base 把读者分析放进交付说明，1016 把利益相关方和关注点列为 SDD 的必需内容。
4. **设计视点与记法**：用表格列出选用的视点、它覆盖的关注点编号、记法（如 UML 组件图、IDEF1X、伪代码）、所在章节；每个关注点至少出现在一行里。对照见"写作规则 · 视点与视图"。
5. **设计决策**：从外部看软件怎样满足需求的行为决策，以及影响模块划分的其他决策。写法见"写作规则 · 决策"。
6. **体系结构设计**（对应项目里的"概要设计"）：
   1. 模块表：每个模块一行，列为标识符、名称、功能、分配给它的需求和决策、开发状态、计划占用的硬件资源、代码位置（程序库或仓库路径）。
   2. 层次与关系：用图或表画出模块的层次、调用关系和静态关系（如"组成"）。
   3. 全局数据结构：常量、变量、数据结构，各写名称、功能、定义、取值。
   4. 执行概念：模块之间的控制流、数据流、状态转换、时序、中断、异常、并发，以及对象和进程的动态创建与删除。
   5. 接口设计：接口标识、接口图、每个接口的特性。
7. **详细设计**：每个模块一节；几个模块共用同一设计时可以合为一节。内容见"写作规则 · 详细设计"。
8. **数据库设计**（可选：有数据库时加）：数据库级决策、按设计层级的数据元素、访问数据库的模块。
9. **运行、出错处理与维护设计**（可选：写 SSDD，或文档覆盖两个以上可独立部署的程序时，写成独立一章；其余情况下，出错处理写进第 7 章各模块的"逻辑"）：初始化、运行控制、运行结束；出错信息表和补救措施；检测点和检测专用模块。
10. **尚待解决的问题**（可选：条件同第 9 章）：本设计没解决、系统完成前必须解决的问题。
11. **需求的可追踪性**：双向追踪表。
12. **注解**：背景、设计原理（指决策理由的背景）、术语、缩略语（按字母序）、变更历史。
13. **附录**（可选：有需要单独维护的大表、图、分类数据时加）：按 A、B 编号。

## 写作规则

### 依据与命名

- 只在合同、项目或用户要求时，在"引用文件"里列 8567、1016、15289。没有要求时正文不引用标准，审查清单里关于依据、IEEE 1016、15289 的 3 条标"不适用：未引用标准"。
- 用户要"概要设计说明书"或"详细设计说明书"时，按 8567-2006 SDD 第 4 章、第 5 章的内容写；需要写依据时写 GB/T 8567-2006。
- 文中声明参照 IEEE 1016 时，写成"参照 IEEE Std 1016-2009（2020 年起已非活动，无后继版本）"。
- 引用 15289 的条款号时带上年份，因为条款号随版本变：2019 版的设计说明是 10.15，数据库设计说明是 10.14，接口说明是 10.28。只写"见 15289:2019 第 7.2、10.15 条"。

### 正文与标题

- 正文描述系统，不用"你"称呼读者；句子主语写模块或接口的标识符，如"TMO-WORKER 每秒取出到期订单"。与 base 不同：读者不操作系统，base 清单里"称呼读者用'你'"一条标不适用。
- 一级章节用"必需章节"的固定标题。模块、接口小节标题用"条号 标识符 名称"格式，如"6.5.3 IF-07 订单服务 → 库存服务：扣减库存"，不改成陈述句。与 base 不同：标识符要能全文检索和引用。

### 决策

- 需求已经定死的决策，或推迟到模块设计再定的决策，照实写"本级不作决策，见……"。
- 安全性、保密性、私密性各写一条决策；不涉及的写"不涉及：原因"。
- 设计随运行状态或方式变化时，写明对应哪个状态或方式。
- 写出对不允许的输入或条件的处理。
- 决策的写法见 `blocks/decision.md`；其中"满足的需求、目标或关注点"一律写编号，供确认时核对。

### 视点与视图

- 按利益相关方的关注点选视点，只写用得上的视点；1016 的 12 个视点是起点，可以自定义新视点。
- 每个视图只依一个视点，在视图开头写明视点名称和记法。
- 视点名后括注它回答的问题，如"组成（模块怎么拆）"。读者不熟 1016 时也能看懂。
- 同一设计元素在多个视图出现时，名称和标识符相同，各视图之间的描述不冲突。
- 每条约束写出施加方、受约束方和规则，如"支付模块要求订单模块在 2 s 内返回锁单结果"。
- 本文章节和 1016 视点的对应（供填"设计视点与记法"表）：

| 本文章节 | 1016 视点 | 回答什么问题 |
| --- | --- | --- |
| 第 1 章系统概述（1.2） | 上下文（Context，5.2） | 系统对外提供什么，边界在哪 |
| 6.1 模块表（4.1.1、4.3） | 组成（Composition，5.3） | 模块怎么拆，各管什么 |
| 6.1 模块表的资源列（4.3 e） | 资源（Resource，5.13） | 占用多少资源 |
| 6.2 层次与关系（4.1.2、4.3 b） | 依赖（Dependency，5.5）、逻辑（Logical，5.4）、结构（Structure，5.9） | 谁调用谁，谁依赖谁 |
| 6.3 全局数据结构（4.2）；第 8 章 | 信息（Information，5.6） | 存什么数据，怎样存取 |
| 6.4 执行概念（4.4） | 交互（Interaction，5.10）、状态动态（State dynamics，5.11） | 运行时谁先谁后，状态怎样变 |
| 6.5 接口设计（4.5） | 接口（Interface，5.8） | 怎样正确调用 |
| 第 7 章的算法和逻辑（第 5 章 a、f） | 算法（Algorithm，5.12） | 每个操作内部怎样算 |

### 模块

- 本文的"模块"指 8567 的程序（模块）和 CSCI 部件（软件配置项），全文只用"模块"；8567 部件的属性记为模块表的列。
- 给每个模块、接口分配项目内唯一的标识符，全文用标识符引用。
- 标出每个模块的开发状态：新开发、重用、再工程、为重用而开发；重用的写名称、版本、文档出处。
- 写硬件资源用量时写度量单位，并写出用量基于典型用法还是最坏情况。

### 接口

- 接口图或接口表里标出哪些实体的接口特性已固定，哪些正在开发或修改。
- 每个数据元素逐项写下列属性：名称或标识符；数据类型；大小与格式；计量单位；范围或枚举值；准确度与精度；优先级、时序、频率、容量、序列约束；保密约束；来源与接收者。
- 写通信方法：链路、带宽、消息格式、流控制、路由、寻址、加密、鉴别。
- 写协议：分段、重组、合法性检查、错误控制与恢复、连接的建立、维护、终止、状态报告。
- 每个接口写出超时值、失败时的重试次数和间隔，以及幂等由哪一端保证。
- 对方实体不在本文范围时，写成"当 X 这样做时，本模块将……"。
- 两端对同一数据的期望不同（如大小、频率）时，分别写出两端的期望。

### 详细设计

每个模块一节，按下面的顺序写：

- 本模块的设计决策，包括选用的算法。
- 约束、限制和非常规特征。
- 实现语言和项目规定的语言不同时，写出语言和理由。
- 由脚本、DBMS 命令、联机查询、GUI 构造器输入构成的模块，列出命令或引用说明它们的手册。
- 输入、输出和局部数据分开写；涉及数据库的引用 DBDD 或第 8 章。
- 逻辑：启动时生效的条件、交出控制的条件、对每个输入的响应和响应时间、运行中的操作序列、异常与错误处理。

算法和记法：

- 每个算法写出输入、处理步骤（伪代码或判定表）、输出和边界条件，细到程序员能编码、测试人员能据此写单元测试；有性能要求时写时间或空间上限。
- 全文同类内容（如各模块的逻辑）用同一种记法，并在"设计视点与记法"表里写明。

### 数据库

- 写出所用 DBMS 的名称和版本。
- 写出可用性、保密性、运行连续性的级别，以及一致性、完整性、业务规则在哪一层怎样实施。
- 写出备份与恢复策略，以及备份恢复期间允许的操作。
- 写出索引、存储空间大小、空间回收、初始数据填充和历史数据的捕获方式。
- 设计层级按所用方法学划分（如概念、逻辑、物理），每层用该方法的术语写。
- 数据元素写出技术名称（字段名），数据元素集合体写出表名、记录名或数据结构名，并写明能否被更新。

### 图与引用

- 图表的通用写法见 `blocks/figure-table.md`，引用外部资料的写法见 `blocks/citation.md`。
- 每张设计图后配文字说明：图的目的、图中每个元素、元素之间的关系。
- 同一信息只在一处完整描述，其他位置引用条号；已有数据字典、协议标准、界面标准时，引用它们。
- 引用 IDD、DBDD 等外部文档时，在本文写一句被引内容的要点，读者不翻外部文档也能看懂本节。

### 追溯

- 追溯的写法见 `blocks/traceability.md`；上游条目是需求，下游是模块。
- 没有需求编号时，追踪表的需求列改用第 3 章的关注点编号，并在基线里写"需求未成文：【待补：需求文档或编号】"。

## 示例

改写前（SDD 接口一节）：

```markdown
### 订单接口
订单服务调用库存服务扣减库存，传入商品和数量，超时会重试。
```

改写后（按本文件"必需章节"编号）：

```markdown
#### 6.5.3 IF-07 订单服务 → 库存服务：扣减库存
- 调用方式：【待补：同步或异步、协议】。
- 已固定接口特性的一端：【待补：订单服务或库存服务】。
- `sku_id`（商品）：【待补：类型和长度】；来源订单服务，接收方库存服务。
- `quantity`（数量）：【待补：类型、单位、范围】。
- 超时：订单服务等待【待补：库存服务承诺的响应时间上限】。
- 重试：订单服务重试【待补：次数和间隔】。
- 幂等：【待补：由哪一端保证，凭什么键去重】。
- 追溯：【待补：需求编号】。
```
