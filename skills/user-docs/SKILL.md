# 软件用户文档

用户文档只有一个目的：让用户在**此刻**完成他要做的事。所以动笔前先弄清两件事：读者是谁，他现在处在什么状态。

## 先弄清读者和任务

"开发者""用户""运维"这种笼统的说法不够用。要具体到一类人：第一次接触产品、想评估能不能用的开发者；已经在生产环境用了半年、遇到具体问题的运维。然后列出他们要完成的任务。文档围绕这些任务组织，不围绕产品有哪些功能组织。

读者混杂时，主线照顾多数读者，少数读者需要的细节放到链接后面或折叠起来，别让所有人都读一遍。

## 四种需要，一篇只服务一种

同一个人在不同时刻需要的文档完全不同。判断标准是两个问题：读者是在**做事**还是在**求理解**？是在**学**还是在**干活**？

| | 学（获取能力） | 干活（应用能力） |
| --- | --- | --- |
| **做事** | 教程 | 操作指南 |
| **求理解** | 解释 | 参考 |

最常见、也最伤文档的毛病，就是把这几种混在一篇里：教程里插大段原理，操作指南里讲概念，参考文档里夹教学。读者是来做一件事的，却被迫读完另一件事。写到一半发现要讲别的，就把那部分拿出去单独成篇，原处放一个链接。

难易不是分类依据。操作指南可以讲最基础的操作，教程也可以教复杂的东西。

### 教程：带新手做成一件事

读者在学，他可能连该问什么都不知道。所以责任全在作者，不在读者。

- 开头告诉读者跟着做完会得到什么。
- 每个读者每次照做都必须成功。用样例数据和事先准备好的环境，让所有人看到同样的结果。
- 让读者尽早看到结果，而且每一步都有看得见的结果，再小都行。写出每步的预期输出，以及出错时会看到什么。
- 只给一条路。不列选项，不讲替代做法。
- 解释压到最少。一句话交代为什么，再链接到解释文档。
- 尽量让步骤可以重做。读者随时都能回到起点重来。

快速入门就是范围收得最窄的教程：用最短的路径拿到第一个可见结果。

### 操作指南：帮会用的人解决具体问题

读者已经会用产品，手上有一个明确的目标。

- 从用户的目标出发，不从产品的功能出发。"如何配置断线重连的退避策略"是一个目标；"点击**部署**按钮"只是一个操作，不值得单独写一篇。
- 标题写出要达成的事，比如"如何……"。
- 面对真实世界的复杂情况。可以有分支："如果是 X，就做 Y。"
- 只写行动。不教学，不讲原理，不跑题。
- 不必从头讲到尾。从合理的位置开始，到读者能接回自己工作的地方结束。实用比完整更重要。

### 参考：供人查阅的准确描述

读者已经懂了，只是要查一个细节。

- 只描述，不指导，也不解释。中立地陈述事实：有哪些参数、什么类型、默认值是什么、什么条件下报什么错。
- 结构跟产品自身的结构一致。代码有哪些模块，文档就有哪些模块。
- 同类条目用同一种格式，让读者在预期的位置找到预期的信息。
- 给简短的用法示例，但不要展开成教程。
- 必须准确、完整。参考文档里漏掉一个参数，就是一个缺陷。

### 解释：讲清为什么

读者想理解，不急着动手。

- 用一个真实或假想的"为什么"问题给这篇文章划定边界，不然解释会写个没完。
- 讲背景：设计决策、历史原因、约束条件。
- 把这个主题和别的东西联系起来，包括别的系统、别的做法。
- 可以有观点，可以权衡替代方案："有人偏好 W，因为……，但……"
- 不夹带操作步骤和参数清单，那些放进操作指南和参考。

## README 是入口

README 的读者是第一次来到这个项目的陌生人。读者不是你。

README 要让他很快回答这几个问题：

- 这是什么？
- 为什么有用？
- 现在是什么状态？已弃用、实验性、还没正式发布的，都要写明。
- 怎么开始？给出能直接复制运行的最短路径。
- 遇到问题去哪里求助？
- 谁在维护？

更深的内容链接到对应的教程、指南、参考，不要都塞进 README。

## 极简

只写用户完成任务需要的关键信息，再加上保证完整所需的最少其他内容。删掉作者觉得有趣、但用户用不上的东西。

软件对操作的反应是结果，不是一个步骤。把它写在对应步骤里，不要单独编号。

## 文档要和产品一起活着

- 改代码时，在同一次改动里改文档。
- 少而准确的文档胜过多而陈旧的文档。发现错的就删。
- 通用的技术和流程不要自己再写一遍，链接到权威来源。

## 用读者验证

衡量一篇用户文档好不好，只看一点：目标读者第一次照着做，能不能完成任务，能不能很快找到要查的信息。

能实际运行的命令和代码，写完就亲自运行一遍，核对输出和文档写的是否一致。没法亲自验证的，在交付时告诉用户哪些没验证过，并建议找一个没用过产品的人照着文档试一遍。
