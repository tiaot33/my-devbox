# 架构与设计描述

架构文档不是系统的全貌照片，而是**为特定的人回答特定的问题**。同一个系统可以有好几份描述：给新人的、给运维的、给评审会的，各自回答不同的问题。

从高层架构到详细设计，用的都是同一套思路，区别只在读者是谁、关心什么。

## 从人和他们的关注点出发

不要从"系统有哪些组件"开始写，要从"谁要读、他想知道什么"开始。

- **先列出利益相关方**：开发者、新加入的成员、相邻系统的开发者、运维、测试、维护者、安全审计、做决策的管理者、采购方。不只看能影响系统的人，也要看受系统影响的人。
- **再列出他们的关注点**，最好写成问题，比如：
  - 系统怎么部署？
  - 某个服务挂了会怎样？
  - 数据存在哪里、谁能访问？
  - 加一个新的支付渠道要改哪些地方？
  - 运行成本是多少？

关注点可能表现为需求、目标、约束、假设、依赖、质量属性、风险。一个关注点可能被好几方共同关心。也有人的关注点和系统的成功相悖，比如攻击者，这类关注点同样值得考虑。

只写利益相关方真正需要的。每多写一部分，就多一份维护负担。拿不准时，问用户读者是谁、他们要用这份文档做什么。

## 用视图回答关注点

一个视图就是从某个角度看系统，用来回答一组关注点。常用的角度有：

- **上下文**：系统的边界在哪，和哪些人、哪些外部系统打交道，交换什么。
- **分解**：系统拆成哪些部分，每部分负责什么。
- **依赖**：各部分之间谁依赖谁，改一处会影响哪里。
- **信息与数据**：有哪些持久数据，怎么存储和访问。
- **接口**：对外和对内提供什么契约，怎么正确调用。
- **交互**：完成一个关键场景时，各部分怎样协作、按什么顺序。
- **状态**：关键对象有哪些状态，遇到什么事件怎样迁移。
- **部署**：运行在什么基础设施上，各环境有什么不同。
- **资源**：资源的使用、争用和性能。

不必每个角度都写。挑能回答读者关注点的那几个就够了。两条底线：每个关注点至少有一个视图回答它；一个视图如果不回答任何人的关注点，就删掉。

视图不一定是图。文字叙述、表格、职责清单、用例描述都可以，哪种最能回答问题就用哪种。

## 控制抽象层级

从外往里逐层放大：先是系统和它的外部环境，再是系统内部可以独立运行或部署的单元（应用、服务、数据库），再往下才是单元内部的组件。

多数读者只需要前两层。组件级只给重要、复杂、有风险或常变动的部分画。代码级的结构交给 IDE 按需生成，写进文档很快就会过时。

**一张图只用一个抽象层级。**服务和类画在同一张图上，读者就分不清自己在看什么了。

## 图要能独立看懂

读者不读正文，只看图，也应该大致看懂。

- 标题写明这是什么图、范围是什么，比如"订单系统的部署图（生产环境）"。
- 每个元素写明名称、类型和职责。适用时写出所用的技术。
- 每条连线都有标签，写出具体意图，并且和箭头方向一致。"发送订单创建事件"比"使用"有用得多。服务之间的调用写出协议。
- 形状、颜色、线型、缩写的含义都放进图例。不要让颜色成为唯一的区分手段。
- 多张图之间，同一个东西用同一个名字、同一种画法。

## 视图之间要对得上

同一个元素出现在不同视图里，名字和含义要一致。视图之间的关系要写出来，比如部署图上的某个容器运行的是分解图里的哪几个模块。

已知的不一致、尚未完成的部分、未决问题，都明写出来。不要假装文档是完整的。

## 决策连同理由一起记

架构文档最有长期价值的部分，往往不是"系统是什么样"，而是"为什么是这样"。

值得记录的决策，通常有下面这些特征之一：

- 影响很多利益相关方；
- 实施代价高；
- 改起来代价高或者风险大；
- 推理过程不直观；
- 和重要的质量需求相关。

每个决策写清这几项：

- 决定了什么；
- 回应哪个关注点；
- 依据的约束和假设；
- 考虑过哪些备选方案，各自有什么后果，为什么没选。

没有定下来或者推迟的决策也要明写：现在是什么状态，等什么条件才能确定。

## 写到设计层时

越往细节写，读者越可能是要照着实现或维护的开发者，要求也越精确：

- **设计元素要分清**：有哪些实体，它们之间是什么关系，有哪些属性，一个元素对另一个元素施加了什么约束。
- **接口站在接口的角度写**：数据写到类型、格式、单位、取值范围；对每种输入怎么响应、多久响应；出错和异常时怎么处理。对方系统不归你描述时，写成"当对方这样做时，本模块会……"。
- **依赖运行状态的设计**：写明它依赖哪种状态或模式。
- **每个模块、接口、数据元素给一个稳定的名字或编号**，便于追溯到需求，也便于测试引用。

## 每份文档自成一体

读者不应该为了读懂这份文档，先去翻好几份别的文档。理解本文必需的要点，就在本文里交代清楚。细节可以链接出去，但主线不能断。

同一个信息只在一处完整描述，其他地方引用它。

## 从现有系统反推时

从代码和配置反推设计时，只写能从材料里确认的内容。推测出来的意图和理由标明是推测，确认不了的列为未决问题，交给用户补。
